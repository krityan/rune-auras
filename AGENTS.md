# RuneAuras

A RuneScape 3 (BETA client) Lua plugin that lets players create **auras**: on-screen UI elements showing game data. An aura pairs a **display type** (how it is drawn, e.g. a bar) with a **data source** (what it shows, e.g. adrenaline). Players create and edit auras in game; nothing is shown by default.

## Before writing code

- **Read `CODE-STANDARDS.md` first**, before the first edit, not after. The rule most often missed: comments are short (one sentence is normal, three is long), and a game fact is explained once, where the code enforces it. The background and the evidence for it (what a probe found, counts, history) go in this file, not in code comments.
- **Before calling a change done,** check the diff against "Reviewing against these standards" at the end of `CODE-STANDARDS.md`. Temporary `DEBUG` probes are exempt: they're removed.

## Running and testing

- **Never change `plugin.json`'s `name`**: the client saves a plugin's PersistentDB keys under it, so a new name opens an empty store and players lose every aura. It's `RuneAuras`; saves from before the rename (under `Rune Auras`, with a space) aren't read.
- `deploy.ps1` copies every `.lua` file, `plugin.json` and `resources/` (PNGs) into `C:\ProgramData\Jagex\RuneScape-BETA\dev_plugins\rune-auras`. Reload the plugin in the client (`prl rune-auras`) to pick up Lua changes. New or changed resources, and new Lua files, need a plugin refresh (`prf`) or a client restart: a reload leaves `Plugin.resources` as it was, and doesn't find a file the plugin didn't have. It also writes `UI/Windows/dev-build.lua` there, which turns the debug options on (see `UI/Windows/debug-options.lua`); a release must not include it. `deploy.ps1 -Production` leaves it out (and removes one an earlier deploy wrote), so the deployed copy runs as a release does. It never deletes files, so remove renamed or deleted modules from the target folder by hand.
- There is no Lua toolchain installed. Syntax-check with the `luaparse` npm package (`luaVersion: '5.3'`) from a scratch directory. Behaviour can only be verified in game, so say so rather than claiming a change works.
- `GAME-TESTING.md` lists what the code relies on that hasn't been checked in game, each with how to check it. Add an unchecked fact there, not as a `TODO` in a comment or here, and delete it once checked (fixing the code if it didn't hold).
- The client runs Lua 5.3+ (`//` and bitwise operators are fine).

## Learning the plugin API

- **Never read other people's plugins.** Jagex's AI guidelines don't allow AI to read other developers' plugin code. Don't open, extract, search or copy from installed plugins (`C:\ProgramData\Jagex\RuneScape-BETA\plugins\`) or anyone else's dev plugins, including PrettyUI's source. Learn the API from the official docs and the stubs, from this file and this repo's own code, and by probing in game.
- **Official docs:** [developer.runescape.com/rs](https://developer.runescape.com/rs/getting-started.html), Jagex's documentation of the RuneScape Client API. It has a tutorial, plugin structure, cheat commands, the API reference (Core: events, input, HTTP, `PersistentDB`; Game: player, world, inventory, config types, entities; Ui: components, layouts, style sheets; Audio, Math, Requests) and the submission guidelines. Check it first, then the stubs.
- **API stubs:** the LuaLS stubs at `../runescape-api-stubs` ([FriendlyDevelopment/runescape-api-stubs](https://github.com/FriendlyDevelopment/runescape-api-stubs)) fill in what the docs leave out, and `.luarc.json` points the language server at them. Check them before guessing at a member.
  - `types.lua` holds the globals (`id`, `config`, `var`).
  - `generated/` documents every class: config types such as `StructType`, `EnumType`, `DBTableType` and `DBRowType`, plus the `ui.*` components.
  - `csvs/` lists names by id (`Sprite.csv`, `VarPlayer.csv`, `VarClient.csv`, ...): grep them offline instead of probing in game. They lack Enum, Struct, Param and DBRow names.
- **Enumerating config:** every `id.<Type>` has `FromID(id) -> name` and every `config.<Type>` has `FromID(id) -> config`. Walking ids from 0 until a long run of misses lists every config of a type. `pairs` works too on `config.Struct`, `id.Struct`, `config.Enum`, `id.Enum`, `config.DBRow`, `id.DBRow` and `config.DBTable` (their metatables have `__pairs`): on `id.Struct` it gives each id that exists and its name, in rising order, and its iterator keeps its own place, so it can be kept and stepped a batch per `Logic` tick with other config read in between (checked in game: the same 35,926 structs as walking ids, which tries 58,616). Spread either over `Logic` ticks: there are tens of thousands of structs.
- **rsprite** (dev plugins `rsprite` and `rsprite-finder` in `dev_plugins/`): a sprite name/id lookup and search library, plus an in-game finder for browsing sprites. Use the finder to find icons while developing. RuneAuras doesn't depend on it: it isn't published (dev dependency by name only), and `id.Sprite[name]` / `id.Sprite.FromID(id)` cover what we need at runtime.
- **PrettyUI** (6398181): the UI library, injected as the global `prettyui` through `requiredDependencies` in `plugin.json`. Look it up when it's needed (see `getPrettyUI` in `UI/Windows/main-window.lua`), not at load: a dev plugin can load before its dependencies.

Key client APIs used here: `ui.Layer/Rectangle/Text.new`, component `SetPos/SetSize/Subscribe/MoveToFront/Destroy`, `ui.Hook.*`, `Event.Draw/ServerLogic/ContentLayerReady/GameStateChanged`, `PersistentDB:Get/Set/GetString/SetString`, `var.VarPlayer[name]`, `Player.*`, `id.Font.*`, `config.Enum[name]` (`.values` is a list of `{key, value}`) and `struct:GetParamValue(param)` over `struct.params`, `ui.Sprite` (`spriteID`, `rgba` tint), `ui.RadialProgressOverlay`, `formatStr`, `log`.

Reading an unknown key on a native component or `id.*` table returns nil (or a placeholder) rather than erroring, so a read can't prove a property exists. To discover an API, log the keys of `getmetatable(instance)`; that's how the radial overlay and sprite members below were found.

## Game data

- **Sources and values:** a data source's `read()` returns `curr, max`, and optionally the unrounded `curr` (for a `smooth` source's Smooth fill) and `stacks` (a buff's stack count, for `$stacks`). `dataSources.Details(id)` gives its name, sprite icon and item icon. They're its own unless it has a `details()` function: "Any channel" uses that to name and show whatever is being channelled. `auraManager.Draw` reads both once per source per Logic tick (nothing a source reads changes faster) and passes the details to displays that have `SetDetails(name, icon, object)`, for `$name` and the bar's icon. Sources also say what their values are: `timed` means seconds (bar ticks, the radial swipe), and `state` is `"cooldown"` or `"active"` (buffs, channels) for the Icon display's dimming and hiding. A source that used to have other ids lists them in `movedFrom`; `dataSources.CurrentID` maps every old id (those plus `RENAMED_IDS`) to its current one, and `source-sync`'s `migrateSourceIDs` rewrites saved auras once the catalogues can be read. Cooldown and buff sources are rebuilt from the catalogues, and their ids are named after game config so they stay stable.
- **Player and Target types:** the player's own values (lifepoints, adrenaline, prayer, summoning; `Sources/player.lua`) and values about their target (target lifepoints; `Sources/target.lua`) are data types of their own, Player and Target, which replaced the old Resource type. The summoned familiar's values are the Familiar type (`Sources/familiar.lua`, `Trackers/familiar.lua`), and only there: Player doesn't list them too. Lifepoints (the `LORE_FOLLOWER_LIFEPOINTS` and `LORE_FOLLOWER_BASE_LIFEPOINTS` varbits of varp 5194) has the familiar's name as `$name` (its NPC config, `LORE_NPC_HEAD`) and its pouch's icon (`FOLLOWER_OBJ`); Spell points (`LORE_SPELL_POINTS`, of 60) and Stored scrolls (`COMBATV2_SUMMONING_SCROLLCOUNT`, of 500) have the special move's name and its scroll's icon. The scroll comes from the pouch through `LORE_POUCH_COUNT_ENUM`, read once into a lookup, and the special's name from the scroll's item name (`familiar.SpecialName`: in brackets after "... scroll", else before the brackets). Their labels leave out "Familiar" (the picker lists them under the type), but an aura picking one is named with it (`auraName`, through `dataSources.AuraName`, which the Trigger tab uses: a source whose label could be another type's gives the longer name), and with no familiar out `$name` is that longer name too. The familiar's details are worked out once per familiar summoned. Player is where other values about the player go, such as Autocast Spell (below). **Resource icons:** Prayer points and Summoning points show buff bar sprites (Prayer Points Reduced's, 18857, and Familiar Summoned's, 26095); Lifepoints, Adrenaline and Target lifepoints show images of ours from `resources/DataSourceIcons` (a source's `iconImage`, by name). `dataSources.Details` gives the image where a sprite id goes, cached once loaded (`gameApi.Cached`) so displays see the same image every frame, and also when a source's own `details` give no icon. Every icon drawer takes either (`dataSources.IsImageIcon`, `SourceIcon.ShowSprite`; the Icon display's radial masks with the image): an image is assigned only once its sprite is sized (`NewStill` takes the size, `SourceIcon:Layout` sets an image again) and ignores tints, so an Icon tint doesn't change it. For desaturating, each image has a greyscale copy beside it, `<name>_grey.png` (made by `Tools/make-grey-images.py`), which `dataSources.GreyIcon` gives for it as it gives a sprite's `GreyIcons/icon_<id>.png`; the Icon and Orb displays get grey copies only through it. New images need a `prf`. Source ids don't name their type, so moving a source between types leaves auras alone; a check also saves the type it was picked from (`sourceType`), which `dataSources.CurrentType` corrects on load (to its source's type, or through `RENAMED_TYPES` for a check with no source picked).
- **Abilities** (`Catalogues/ability-catalogue.lua`):
  - The style enums `COMBATV2_ABILITIES_<STYLE>` (MELEE, RANGED, MAGIC, NECROMANCY, DEFENCE, CONSTITUTION; there's no ATTACK or STRENGTH enum) hold `COMBATV2_ABILITY_<SKILL>_<ABILITY>` structs (spells: `MAGIC_<SPELL>`). Each has `COMBATV2_ABILITY_NAME` and `COMBATV2_ABILITY_ICON` (a sprite id) params.
  - The name normally matches the cooldown vars `COMBATV2_COOLDOWN_<name>_START/_END`. `VAR_ALIASES` maps the ones that don't, including shared cooldowns (Dive uses Bladed Dive's vars). Only abilities with both vars are listed. Two structs of one ability can share a var: `REPLACED_BY` leaves one out in favour of the other, which takes its id as `movedFrom` so auras saved with it follow (Magma Tempest's main struct, `MAGIC_MAGMA_TEMPEST`, is named "Magma Tempest (Targeted)", its targeted mode; `MAGIC_MAGMA_TEMPEST_REVOLUTION` is listed as plain Magma Tempest).
  - Greater versions have an unlock flag `COMBATV2_ABILITY_<SKILL>_GREATER_<ABILITY>_UNLOCKED` and a struct of the same name with the greater icon. `GREATER_ALIASES` and `GREATER_ICONS` cover the exceptions. Greater Barge, Flurry and Fury are unlocked from codices in Elite Dungeon 2 and have neither: `ED_GREATERS` gives each its unlock flag (`DUNGEON_REWARD_SHOP_<ABILITY>_OVERRIDE_UNLOCK`) and its `COMBAT_ABILITY_ICON_MUTATED_<ABILITY>` sprite (840 to 842). They switch in via `ApplyGreaterUnlocks`, which `source-sync.lua` runs (through `dataSources.ApplyGreaterIcons`) from two server ticks after the player is available, retrying each tick (up to `GREATER_MAX_TICKS`) until every flag has been read; after that `OnVarChanged`, fed from `var-changes`, follows flags that arrive late or change mid-session. The flags are varbits, whose changes arrive only under their base var's name, with its whole value, never under the flag's own name. So the abilities are indexed by the base var's name (`indexUnlocks`) with each flag's mask (`gameApi.VarBitMask`), and a change tests the base value against it.
- **Cooldowns** (`Trackers/ability-cooldowns.lua`):
  - Timed from the `_START`/`_END` server-tick vars, using the module's own tick clock: counted `ServerLogic` events, synced whenever a `_START` changes.
  - `_START` values sent on entering the game are ignored for a few ticks.
  - After a reload no `_START` changes until an ability is used, so `ServerTick()` syncs the clock from the latest `_START`'s VarClient counterpart, `COMBATV2_COOLDOWN_<name>_START_CLIENT`: the client Logic tick of the same cast. `_END_CLIENT` is the Logic tick it ends on (-1 if never used; probed in game, it matches `_END` to within a Logic tick), but it only helps while a cooldown runs, and there's no `_CHARGE2_` VarClient, so a recharging second charge couldn't sync it.
  - Before the clock is synced, the highest known `_START` (every ability is registered with `Watch`) is a lower bound on the server tick, so cooldowns that ended before it already read as ready.
  - **Special attacks** with a cooldown (Instability from the Fractured Staff of Armadyl, Blackhole, Crystal Rain, Power of Darkness, Icy Tempest, Vine Call, Soulfire, Igneous Showdown, Sunfall Slam, Fishstabber, the Necromancy guards' Death Grasp, Death Essence and Soul Crush, and Sanguine Volley) are sources of their own data type, Special attack cooldown (`specialAttack`), as they aren't abilities. `GameData/Catalogues/special-attack-catalogue.lua` lists them from the debuff the game shows while one is on cooldown, which the buff catalogue finds: `COMBATV2_ABILITY_WEAPON_<key>_COOLDOWN` with cooldown vars `COMBATV2_ABILITY_WEAPON_COOLDOWN_<key>_START/_END`, or for the guards and newer weapons `COMBATV2_DEBUFF_<key>_WEAPON_COOLDOWN` with `COMBATV2_COOLDOWN_WEAPON_<key>_START/_END` (`COOLDOWN_DEBUFF_NAMES`). Malachi's tooth's debuff is named after the weapon (`COMBATV2_DEBUFF_RANGED_GHRAZI_CROSSBOW_T95_WEAPON_COOLDOWN`, found by a probe matching structs on their name param, as their struct names don't say) but its vars after the special (`COMBATV2_ABILITY_WEAPON_COOLDOWN_SANGUINE_VOLLEY_*`), so `SPECIAL_KEYS` maps the one to the other. The vars are server ticks, timed by this tracker like an ability's (its `COOLDOWN` and `_START`/`_END` checks match them). `buffCatalogue.Load` always builds the cooldown debuffs up front (`specialAttackCatalogue.IsCooldownDebuff`: about a dozen), so the sources come with the buffs. Each is labelled with its weapon's name (without a trailing " (tier N)": every Death guard tier shares Death Grasp), which players search for, with the special's own name as `$name`. Source ids are `special_attack_<key>`. "Equipped weapon" (`special_attack_equipped`, listed first, like "Any channel") shows the worn weapon's special: the main hand's (worn slot 4), where every special with a cooldown is (Necromancy guards included). While a special is worn, the aura manager reads that special's own source in its place (`readSourceID`, `dataSources.EquippedSpecialID`), so values, conditions and load checks follow it. Its Trigger tab has two options, in the aura's `sourceOptions` (the `SourceOptions` record in `aura-record.lua`: options only some sources have, saved only while ticked and dropped when the source changes): Remember last weapon (`rememberSpecial`) keeps reading the last special worn this session after a switch to a weapon without one (not saved: a reload forgets it), and Hide without a special (`hideWithoutSpecial`) unloads the aura while it stands for no special, like a load option, so a dynamic group closes up. `Trackers/worn-equipment.lua` reads every worn slot from the worn inventory (94) when `InventoryAdded`/`InventoryUpdated` says it changed, for any source that needs equipment. Every version of a weapon (augmented, dyed, Third Age) has `COMBATV2_SPECIAL_ATTACK_BASE_ITEM` naming its plain version, which is the debuff's item a special is listed under ; a weapon that misses is matched by its name without a tier, for the Death guard tiers the debuff doesn't name (both in `specialAttackCatalogue.Find`, which gives the special's key). **An essence of finality amulet's stored special isn't offered:** the API can't read it yet, and is expected to (a source that learned it from use was tried and dropped as not quite reliable). What was found: the amulet (`ENCHANTED_ALCHEMICAL_HYDRIX_AMULET_*`, one item per colour, worn slot 3) has no param for it and no var changes when it's stored (`ITEM_DEGRADE_KEEP_OBJVARS` says it's in the item's vars, which the API doesn't support; the slot's, inventory's and item's metatables have only their documented members). The client draws its hover tooltip, which names the special, outside any interface (a sweep of every loaded interface's text found none of it). Using the stored special sets that special's own cooldown vars (Instability's, shared with the staff), so a learned special could be timed, but specials without a cooldown can't even be learned: `COMBATV2_JUST_USED_ABILITY` (VarPlayer and STRUCT VarClient) only names the amulet's generic ability, `COMBATV2_ABILITY_CONSTITUTION_ALCHEMICAL_HYDRIX_AMULET` (11748), whatever it holds. They have no second charges, so no Charges check. Not all have a `_START_CLIENT` (Soul Crush's hasn't), so only abilities' `_START`s sync the clock after a reload (`syncStart`, which skips `COMBATV2_COOLDOWN_WEAPON_`); special attacks still count towards the lower bound. Most do have an end VarClient, `COMBATV2_COOLDOWN_WEAPON_<key>_END_CLIENT` (the guards' vars plus `_END_CLIENT`; `endClientVar` in the catalogue, passed to `Watch`), the Logic tick the cooldown ends on: with no ability use to sync from, a special still on cooldown syncs the clock from that and its `_END` (`syncFromEndClient`), so a reload mid-cooldown still times it. `Data/specialAttacks.txt` (local) lists every special attack from the wiki and how each is tracked: most have no cooldown. Balance by Force and Phantom Strike have no cooldown vars by name; `COMBATV2_ZAROS_SPEC_COOLDOWN` and `COMBATV2_EGWD_JAS_BOSS_MAGIC_WEAPON_SPEC_COOLDOWN_CLIENT` are VarClients that may be timers, unprobed.
  - **Charges:** Surge, Escape and Barge can hold a second charge, timed by `<base>_CHARGE2_START/_END` (Barge's `_END` has no name in the var list, so it's untested); Backhand, Binding Shot and Impact by `<base>2_START/_END` (`COMBATV2_COOLDOWN_ATTACK_BACKHAND2_START`), which work the same (logged in game for all three). `SECOND_CHARGES` in `ability-cooldowns.lua` names each one's pair. Seen in game with Surge: using a charge while both are ready sets only CHARGE2 and the ability stays usable; using the last sets the base vars, whose cooldown runs until a charge is back, and `CHARGE2_END` is when both are. So `GetCharges` is 0 while the base cooldown runs, 1 while only CHARGE2 does, else 2. Nothing says whether the player has a second charge (all read 0 until used), so an ability counts as having one once a CHARGE2 var is seen above 0, saved as `abilityTwoCharges`; until then its most is 1. Cooldown sources report charges as their fourth value (where buffs report stacks), for `$charges` and the Charges check. Their time is `GetNextCharge`: the base cooldown while no charge is left, else the second charge recharging, so Surge shows a cooldown after one use too. Its Icon isn't dimmed while a charge is left (it's usable), and an Active check on it means recharging; use Charges to test whether it can be cast.
  - **Recast stages:** Dismember turns into Slaughter, then Massacre, and Spectral Scythe has two stages too. Each stage is `COMBATV2_ABILITY_<var name>_RECAST_<n>` (its name and icon), with a flag `COMBATV2_ABILITY_<var name>_RECAST_<n>_ACTIVE` (1 while it's the stage to use next) and cooldown vars `COMBATV2_COOLDOWN_<var name>_RECAST_<n>_START/_END` (and `_CLIENT`): the 3-tick global cooldown after the stage before, which isn't shown. Using the ability sets its own cooldown (Dismember's 40 ticks) and RECAST_1's flag; each recast clears its flag and sets the next one's; using the last clears it, leaving the ability on its own cooldown. The catalogue finds them by name (`abilityStages`, up to `MAX_STAGES`), and the cooldown source reads the current stage (`currentStage`: the last flag set; the game clears them all when the last stage is used or the ability's cooldown ends): it shows as ready, with the stage's name and icon (`details`). The flags are cached from VarTransmit with the cooldown vars (`abilityCooldowns.WatchFlag`).
  - **Conjures and commands:** while a Necromancy conjure is out, the action bar shows its command in its place. `COMBATV2_ABILITY_NECROMANCY_CONJURE_<NAME>_ACTIVE` is 1 while it's out and 0 once it's gone (logged in game with the skeleton warrior; the putrid zombie, vengeful ghost and phantom guardian have the same vars), and the command has its own cooldown vars (`COMBATV2_COOLDOWN_NECROMANCY_COMMAND_<NAME>_START/_END`), which conjuring starts. `COMMANDS` in the ability catalogue links each conjure to its command (`AbilityEntry.command`), and the cooldown source shows the command's name, icon and cooldown while the flag is set (`activeCommand`). Conjure Undead Army is left out: it summons up to all four, so which command isn't known.
  - **The action bars** (`Trackers/action-bar.lua`): the main bar and up to four more are `TOPLEVEL_V2_COMBAT_BAR` and `_BAR2` to `_BAR5`, each with 14 slots of `GRAPHIC_<n>` (the ability's icon as `spriteID`, or an item as `associatedObjectID`), `COOLDOWN_<n>` (a sprite stepping through a swipe animation, 14521 to 14642, while it cools down; every slot runs it on the global cooldown), `TEXT_<n>` (the keybind, "1", "c-Q", "F1"; `actionBar.Keybind` gives an ability's first slot's, the main bar's slots 1 to 14 first, then each additional bar's) and other parts. A slot holding an item keeps the `spriteID` of whatever it showed before (an ability swapped with an item leaves its icon id in the item's slot, with `associatedObjectID` the item and `opBaseName` its name; an ability's slot reads -1 there), so `actionBar` skips slots showing an item; `TOPLEVEL_V2_PARENT_SUBOVERLAY_ACTION_BAR` and `COMBATV2_ACTIONBAR` are other layouts, unused here. A slot's `GRAPHIC_<n>` names its ability in `opConfig.opBaseName` ("Greater Sunshine") and is tinted `rgb` 0x333333 while the game shows it as unusable (another style's weapon, a missing shield, too little adrenaline for its current cost), 0xFFFFFF otherwise (logged in game). Those members are the base component's, which a class's metatable doesn't list, so a probe has to name them. The ability's current adrenaline cost shows only in its hover tooltip (`TOPLEVEL_V2_ABILITY_BOOK_TOOLTIP__REQ_TEXT_2`, `100%` then `55%` for Greater Sunshine), so the tint is the way to read it. No var holds that cost: logging every VarPlayer change and every INTEGER VarClient while it changed showed only the buffs that cut it, so the client works it out from them (Charged Greater Flow took Greater Sunshine from 100% to 55%; 5 Glacial Embrace stacks, `COMBATV2_BUFF_GLACIAL_EMBRACE_STACKS`, took Tsunami to 40%, and 20% with Greater Flow too). Rebuilding the cost would mean hand-writing every reduction and how they combine, so it isn't. `actionBar.IsUsable` reads every shown slot's icon and tint at most every 10 Logic ticks, only while asked (the keybind texts at most once a server tick, on the first read in it: they only change when the player edits them, and a keybind belongs to its slot, so it stays right when abilities move), and finds an ability by any icon it can have (its own, greater, recast stages', its command's): usable if any such slot is undimmed, nil if none is shown.
- **Autocast spell** (`Trackers/autocast.lua`, source `autocast_spell` in the Player type): the spell set to autocast, which becomes the Magic basic attack. `AUTOCAST_SPELL` (a varbit, bits 1-16 of VarPlayer 0 `LASTCASTSPELL`) holds the spell's `COMBATV2_ABILITY_ID` (Blood Barrage 102, Exsanguinate 215, Incite Fear 214), which is also its key in the `COMBATV2_ABILITIES_MAGIC` enum, so `abilityCatalogue.MagicSpell` reads its name and icon from the struct under that key (the catalogue's own list leaves out spells with no cooldown, the combat spells among them). The tracker reads each spell once, and remembers one the enum doesn't list as missing, so it isn't searched for again. It's 0 with none: clearing autocast sets it to 0 and leaves `AUTOCAST_SET` (bit 0) at 1, so that bit isn't read. It's read through `varCache`, as its changes arrive as `LASTCASTSPELL`. The source is on/off (1 of 1 while a spell is set) and named and shown as the spell, or the last spell set once it's turned off (dimmed, as an inactive source). The last spell is saved (PersistentDB key `autocastSpell`, its ability id) so it's still shown after a reload with autocast off; before any has been set it's named "Autocast Spell" with the placeholder icon. Spells that can be autocast have `COMBATV2_CAN_BE_AUTOCAST` 1. `AUTOCAST_SPELL_OVERWORLD` (on `LAST_AUTOCAST`) and `AUTOCAST_DEFMODE` stayed 0 with Ancient spells set, so they're unused. Casting a spell by hand doesn't change it.
- **Stalled ability** (`Trackers/stalled-ability.lua`, data type `stalledAbility`, one source `stalled_ability`): an ability used with nothing to hit is stalled, and fires on the next attack. `COMBATV2_NEXT_ABILITY` (a STRUCT VarPlayer) holds it: through VarTransmit the struct's id (14688), set on the stall's server tick along with `COMBATV2_JUST_USED_ABILITY`, and -1 once it's cleared (when combat ended, 15 ticks after the stall, in the one probe; firing it on an attack wasn't logged). Read directly it's a struct even with none (`UNKNOWN(-1)`), so the tracker keeps its id. It's read directly until a change brings it, as one unchanged since a reload never comes through. The source's time is the time until combat ends, which clears the stall, plus a server tick: once the game clears it, it's still shown for that tick, its time counting down as before (`HOLD_LOGIC_TICKS`; cleared on the tick it fires, it looked a tick early beside the hit). Past the combat timer's end while still stalled (something it doesn't follow kept combat going) it shows 0.1 s, and with no use seen since a reload it shows the longest window in full. It's named and shown as the stalled (or last stalled) ability, from the ability catalogue by key (`abilityCatalogue.StructKey`, which the channel tracker uses too), so a greater version's icon follows its unlock; before any stall it's named "Stalled ability". The queue vars (`COMBATV2_QUEUED_SLOT`, `_QUEUED_BAR`, `_QUEUE_TRIGGER_TIME`) didn't change on a stall.
- **Combat timer** (`Trackers/combat-timer.lua`): no var holds it (no VarClient changes to a future Logic tick for it, and no VarPlayer near the server tick), only whether the player is in combat (`COMBATV2_PLAYER_IS_IN_COMBAT`, a varbit: its changes come through VarTransmit as its base var `COMBATV2_TEMP_VARP1`, not by name). So it's worked out from ability uses, which the cooldown tracker hands on as it sorts each var change (`abilityCooldowns.SetOnUse`): every cooldown `_START` (a name with COOLDOWN in it, so the global cooldown's too) whose value is fresh, once the tracker is settled. Other vars ending `_START`, such as the Zamorak gear switch timers and the Necromancy conjures' buffs, aren't uses, and the combat timer adds no work per var change: combat ended, and a stall cleared, 16 server ticks after an ability on the global cooldown (`COMBATV2_GLOBAL_COOLDOWN_START` set on the same tick, before or after the ability's own `_START`) and 17 after Surge or Bladed Dive, which aren't on it; a later use restarts it. Being attacked restarts it too, 0s included, and keeps a stall going. No var marks an attack: a hit that does damage drops `LIFEPOINTS`, but an attack that does no damage changes nothing the client is told. Following only the damaging ones would make the timer right for some attacks and wrong for others, so attacks aren't followed at all: the timer follows the player's own uses, and a stall kept going by attacks runs past its end, showing 0.1 s until the game clears it. `COMBATV2_TARGET_EFFECTS_TRIGGER` (with `_EFFECTS_7`) is sent again, unchanged, every 6 ticks while the player has a target, attacked or not, and when the target changes or turns, so it doesn't mark attacks. The player entity has nothing that does either (its only members: `aabb`, `coordGrid`, `displayName`, `facing`, `facingTarget`, `isValid`, `position`, `route`, `routeEnd`, `uid`; `facingTarget` changes almost every tick with movement). Walking out of an enemy's range ended combat (and the stall) at once, 5 ticks after its last attack, with the target dropping. `INVENT_CHARGE` drains every 7 to 8 ticks in combat whatever happens, so it's no help. An auto-attack fires a stalled ability, so it isn't followed.
- **Extra action button** (`Catalogues/extra-action-catalogue.lua`, `Trackers/extra-action.lua`, data type `extraAction`): the button some fights and quests show beside the action bar (Kerapac's Warp time, the God Wars 2 bosses' powers, Fort Forinthry's ballista). `TOPLEVEL_V2_EXTRA_ACTION_BUTTON_ID` (VarPlayer) is the button showing, 0 while none; its `_ID_CLIENT` VarClient follows it (-1 for none). The game sets only `TOPLEVEL_V2_EXTRA_ACTION_BUTTON_COOLDOWN_END` (server ticks, like an ability's: 50 ticks after use for Warp time), leaving `_START` at 0, so the cooldown tracker times what's left (its cache already follows any `..._COOLDOWN_END`) but not the full cooldown. That's measured on each use (`onVarChanged` in the tracker): `_END` arrives on the use's server tick, so it's `_END` minus `abilityCooldowns.ServerTick()` (Warp time: 232111 at tick 232061, 50 ticks), kept per button in ticks until leaving the game (`extraAction.Reset`), unless it's within a tick of the table's (`CLOCK_SLACK_TICKS`: the clock can be a tick either side when `_END` arrives, so one button measured 99 and 100 ticks on different uses; in later checks the clock matched each ability's `_START_CLIENT` exactly, the reload estimate matched the next `_START` after three reloads, and the countdown reached 0 on the `_END` tick, so the cause of the 99s wasn't found), skipped while the cooldown tracker is settling after entering the game (`IsSettled`, as the saved value is resent), while its clock isn't synced, when `_END` moves while the cooldown is still running (not a use), and on the tick the button changes (a measurement taken that tick is undone, whichever var arrives first). The button var arrives through VarTransmit, so it's followed from `var-changes` (read once at load, as a reload in game gets no change for it). While no button shows, the game sometimes sets `_END` to the current tick or one ahead (seen on entering an area with a button and between its phases), and when the button goes it cuts a running cooldown to one tick ahead; so measuring needs a button showing (`isShowing`), and `Read` gives ready while none is, which keeps that one-tick value from flashing a cooldown on the icon. There's no `_END_CLIENT` for this cooldown, so after a plugin reload mid-cooldown it can't be timed until an ability use syncs the cooldown tracker's clock. Until a button is used, its full cooldown is the table's (`extraAction.CooldownSeconds`). The buttons are the 20 rows of DB table `EXTRA_ACTION_BUTTON` (118), each named `EXTRA_ACTION_BUTTON_<key>`; columns: 1 the button id, 2 its name, 3 empty or "", 4 its op ("Activate", "Call upon"), 5 and 6 two sprites (the button switched between the two while in use; probably hover, unchecked), 7 the cooldown in server ticks (empty for buttons without one: Revive, Realm Movement), 8 and 9 a buff's duration and struct (Zilyana's and Kree'arra's, 30 ticks), 10 a description. Nothing indexes the table's rows, so the catalogue walks every DB row's name (`gameApi.ConfigWalk("DBRow")`) in the background on entering the game (`extraActionCatalogue.Load`, from `source-sync`), 500 a Logic tick (about 20,000 rows, under a second), once a session; then `dataSources.RefreshExtraActions` lists the buttons, and auras saved with one show as placeholders until then. Sources: "Any" (`extra_action_button`, listed first under the type; named "Extra action button" until a button has shown) shows whichever button is up, taking its name and icon (`details`); then one per button (`extra_action_<key>`, the row name without the prefix, lowercased), labelled with its name, or with its key added when two listed buttons share one. Buttons only a quest shows aren't listed (`isListed`): their keys start `QUEST_` (Extinction's Leave Erebus, Dead and Buried's Character, Secrets of Amberfell's Inanna's Howl), nor is Revive Player (`REVIVE`, `UNUSED_KEYS`), cut from Zamorak before release. The generic source still names and times them. Per the wiki (checked 2026-11-05), the rest are repeatable content: the Elder God Wars Dungeon's battlefield abilities (Zilyana, Kree'arra, K'ril, Helwyr, Gorvek and Nex, picked from each commander), Kerapac, Zuk, its siege engine and Zamorak; Raksha (`DINO_BOSS`'s Inner power), Solak, the Gate of Elidinis, Zemouregal & Vorkath's ballista, and the Ghrazi Blood Knights' Inanna's Howl. The wiki gives two cooldowns that differ from the table's: Wrath of Nature 60s (table: 300 ticks, 180s) and the Blood Knights' Inanna's Howl 30s (table: 27s). The measurement corrects either after one use; until then the max shown is the table's. All share the one cooldown var, so a button's own source reads the cooldown only while it's the one showing or last shown, else ready out of its own cooldown. Buttons without a cooldown are listed too, and always read ready. "The one showing" is the button up now, else the last one shown since entering the game (`extraAction.ButtonID`). The button's interface is `TOPLEVEL_V2_EXTRA_ACTION_BUTTON` (743); its `BUTTON_GRAPHIC_COOLDOWN` component is a sprite showing columns 5 and 6, while `BUTTON_GRAPHIC` isn't a sprite.
- **Buffs** (`Catalogues/buff-catalogue.lua` and `Catalogues/Buffs/`, `Trackers/active-buffs.lua`): read from the game's own vars, which are exact, and for most of the player's buffs the game's buff bar (below). `active-buffs` reads every kind of buff the same way: what its vars say (whether it's running, and its values: `measureTimer`, `measureStart`, `measureStacks`, `measureToggle`, `measureQuiet`, picked by `measureFor`), then whether a running buff counts as active (`isCountedActive`: its required var, then the bar for a buff the bar decides). Each buff has a run while its vars say it's running (`BuffRun`, `runs`), kept whether or not it counts, which holds a timer's max and the grace (`GRACE_TICKS`, 2 server ticks) a buff seen starting counts as active for, as its requirements and the bar can lag its vars. A buff found already running (an aura made, picked or loaded mid-buff) gets no grace, so it doesn't flash on. Nor does an ability's buff whose ability wasn't reported used within 2 server ticks of its start, either side (`isGraceFromUse`: `COMBATV2_JUST_USED_ABILITY`, which the game sends on every use, two defensives used together included, keyed by the struct's ability, `usedTicks`): some resets rewrite every ability buff's end time to that moment plus its duration, as though each was just cast, with no use reported, which would otherwise flash them all on until the bar check. Praying at the Altar of War resets the running cooldowns (`_START` and `_END` to 0) and then rewrites the end times; Warp time ending (Kerapac) sets every cooldown's `_START` to that tick (and `_END` to it too for those that were ready, or to what's left), so a recent `_START` doesn't mean a use. Only buffs with an icon (a sprite or an item, `HasIcon`) and known vars are listed as sources: we may only show buffs that can appear in the game's buff bar, and only buffs with an icon can (in the dump, every typed buff but Sheer Cold has one). Debuffs (`kind = "debuff"`) are catalogued and read the same way and follow the same rule, listed under their own "Debuff" data type; their source ids still start `buff_`, as the catalogue names every entry. Special attacks' cooldown debuffs (`IsCooldownDebuff`) are left out there, as they're listed as special attacks. So are debuffs that belong to an ability (their struct has an ability id and skill, so `entry.ability` is set: Blood Tendrils, Dismember and its Slaughter recasts, Incendiary Shot, Pulverise): those are the effect the ability puts on the target, shown in the target panel and timed from the player's use, not a debuff on the player. Nothing else in a debuff's params says whose it is (`COMBATV2_BUFF_CATEGORY` 1 holds both kinds).   - **Finding a buff's vars:** nothing in config links a buff to its vars (no enum maps structs to vars), so the catalogue finds them by name, trying `buff-vars.lua`'s name templates in order (`END_VAR_NAMES`, `STACKS_VAR_NAMES`, `ACTIVE_VAR_NAMES`, `START_VAR_NAMES`: `{S}` the struct name, `{C}` its core, `{B}` the struct name without `_STACKS`) after `buff-data.lua`'s aliases and families: the struct name or its core with `_END_EFFECT_CLIENT`/`_END_CLIENT` and a few prefixes. Special attacks' effects leave out the END: `<core>_EFFECT_CLIENT`, plain or under `COMBATV2_COOLDOWN_` (the only five VarClients named that way: Instability, Split Soul and the three DMBH weapons). `COMBATV2_COOLDOWN_<ability>_END_CLIENT` is the ability's cooldown, not its effect (`..._END_EFFECT_CLIENT`), so it's never used. Last, names with no END: the struct's own, `<struct>_COOLDOWN`, `COMBATV2_<core>_COOLDOWN` and `COMBATV2_COOLDOWN_<core>`. - **Target lifepoints** (`Trackers/target-info.lua`, source `target_lifepoints`, a Resource): the current target's lifepoints are the target info panel's `TOPLEVEL_V2_TARGET_INFO__ENTITY_HEALTH_LEFT` text (`"94,903"`, commas and all; `"N/A"` while it waits for a new target's details), exact and changing as hits land. It's read when asked (`targetInfo.Lifepoints`), not on `ServerLogic`: the panel updates after the server tick's event (one Logic tick after it, every time it was logged), so a read then shows the tick before. Reading every Logic tick would mostly find nothing new, so it's read on the first two reads from one Logic tick after each server tick (`gameClock.ServerTickLogicTick`; the second in case the update comes a tick late), and on every read for a new target or while the panel shows `N/A`. No event marks the update: the transmit hooks (`ONVARCTRANSMIT` and the rest) never fire on a component we make, and the NPC entity has no health member. The game gives no max: the player-target HP VarClients (`TOPLEVEL_V2_TARGET_PLAYER_CURRENT_HP`/`_MAX_HP`) stay -1 for NPCs. So the max is worked out from the panel's health bar. The bar's fill, `PROBAR_ACTUAL_HEALTH_LAYER`, is `round(percent * full / 100)` units wide, where percent is the health percent rounded down and full is the width of `PROBAR_FAKE_LAYER` behind it (122 at every interface scale, 70% to 300%: widths are interface units), and it changes on the same Logic tick as the lifepoints text, so the two describe the same moment. At 100% the max is the lifepoints. Below, the max is above lifepoints / (percent + 1) and at most lifepoints / percent, and it's kept within each read's range, so it closes in on the real max as the target's health moves and is exact once the target's seen at full. Before that (a target first seen hurt: targeted mid-fight, or after a reload) the fill is still within a percent of the panel's bar, though the max can be further off at low health (1 / (percent + 1) at most). 0% gives no bound (and is what a bar not yet drawn reads), so it's skipped. The health percent VarClient `COMBATV2_TARGET_SIDE_PANEL_HEALTH` isn't used: it lags the text by several server ticks (it still read 95 with a training dummy back at full for more than 4), and a max worked out from it with lifepoints that had moved on overshot, until a full dummy's bar stopped short of full. The panel's `%` text is the hit chance, not health (below). With no target (the panel unloads) it reads 0 of 0. Its `$name` is the target's name (the source's label until there's one). The same tracker reads the panel's details for the target text fields: `LEVEL` (combat level text, `N/A` while waiting), `TOPLEVEL_V2_TARGET_HITCHANCE` (a VarClient in tenths of a percent, -1 where the panel shows `-`, e.g. training dummies) and the `WEAKNESS` sprite (an attack type's icon: the enum `COMBATV2_ATTACK_TYPE_ICONS` gives each attack type's sprite, read once config can be, and `ATTACK_TYPE_NAMES` names them, as nothing in the game does: 0 none, 1–4 air, water, earth, fire, 5–7 stab, slash, crush, 8–10 arrows, bolts, thrown, 11 magic, 37 necromancy). An enemy targeted within the spread's length, flagged and without a run of its own, gets a run from the death, lasting `spreadTicks`. Enemies it spread to aren't known until targeted: the target var can't always be matched to an NPC (see Which target), so neither the dying target's place nor its neighbours can be. It's on from the cape worn or on the Anachronia base camp's cape stand, so `playerState.HasMagicMasterPerk` reads vars, not the worn item: `SKILLCAPE_PERKS_OBJ` (OBJ) is the worn cape whose perks are in effect (31273 the Magic master cape, 20767 a Max cape, -1 none), and `DINO_BASE_CAMP_PERK_SKILLCAPE` (OBJ) the cape on the stand. A multi-perk cape (by name: max or completionist) holds its perks in `SKILLCAPE_PERKS_STORED1..3` (a perk number; magic is 4) with `..._MASTER` set for the master version (adding the magic master perk to a max cape set `SKILLCAPE_PERKS_VAR1` to 0x80004). The length is taken at the cast and kept on the run (`lengthTicks`). The perk is checked at most once a server tick (a hex aura with no cast asks every Logic tick, and a max cape's check reads its name). A max cape on the stand and the stored perks' numbering beyond magic are unchecked.
  - **Categories:** the type's sources are split into Abilities (timed from a `_START`), Hexes (timed from a cast) and Other (`DataType.categories`, `DataSource.category`), picked in a Category combo before the source (`sourcePicker`; the category picked without a source is kept per aura in the Trigger tab and per check in checks, not saved).
  - **Other** (`targetDebuffCatalogue.OTHER`, `Trackers/target-effects.lua`): effects players put on enemies whose cause can't be followed (Stunned, Bound, Frozen, Poisoned, Bleeding, Pulverised, Haunted, Death Mark, Extreme Vulnerability, Incendiary Shot, the stat drains; Pulverised is also an Abilities entry, which times only the player's own, and is kept here to see anyone's. Blood Tendrils and Sever no longer exist, Deadshot is no longer a DoT, and Provoke shows no icon on the target or the player's buff bar, so it can't be shown at all), hand-picked from the debuff structs: no param says which debuffs can go on an enemy. Each is on (1 of 1) while its icon shows on the current target's panel, read once a server tick; like a run, two reads without it end it, a full panel doesn't, and changing target or the panel unloading ends them all (reads ignore one seen on another target before the next tick drops it). Effects sharing a sprite show as one (Bleeding is also Dismember's icon). Another player's look the same, and a refresh can't be seen. They're on or off only: a Max duration counting down from when the icon first showed was tried and dropped (a saved `sourceOptions.durationSeconds` is dropped on load). Checks on an Other source read it on or off. Which of these the panel shows on an enemy is unchecked.
  - **Debilitated** lasts 13 ticks, longer with a shield or defender (23 with a tier 90 shield, per the wiki), so no fixed length fits. `COMBATV2_DEBILITATE_NPC_UID` names the target while it's on and goes to -1 (or 0) when it ends (an entry's `targetVar`): that ends the run on the target it named and measures its length from the use, which later uses take (`measuredTicks`, until leaving the game). Until one is measured it lasts its usual longest, 23. A run lasts while the var names its target, even past its length, so one longer than the last measured (a better shield, the Bulwark perk) still runs and is measured at its end, reading 0 time left until then. A change to another target isn't an end. The var holds the same uid as `NPCTARGET`, and a measured length matched the panel.
  - **Pulverise**'s Pulverised lasts 50 ticks (its struct's `COMBATV2_ABILITY_EFFECT_DURATION` and the wiki), also unchecked against the panel.
  - Fragmentation Shot no longer exists; its cooldown vars hold Combust's values.

## Auras and UI notes

- **Positions:** an aura's `x/y` is an offset from its anchor (`Auras/Helpers/anchors.lua`, nine points) counting right and up, whatever the anchor, to match the sliders: a top-left aura on screen has a negative `y`, a bottom-right one a negative `x`. Inside a group it's a plain offset (right and up) from the group's point instead (see Groups), and a text node's offset on its display counts the same way. `anchors.ScreenDelta` converts a right/up offset to screen pixels (right/down) and back. Offsets used to count inwards from the anchor (right/bottom anchors leftwards/upwards, the rest rightwards/downwards, and group offsets right/down): `Auras/Store/offset-migration.lua` converts a record once, keeping it where it was on screen. Saves mark each aura's record with `offsetsVersion` (2), added and removed only by `persistence.lua`, so a save that stops partway leaves the rest marked old and nothing is converted twice; imports convert exports older than format 3.
- **Channels** (`Trackers/channel.lua`, data type `channel`): the game has its own channel vars, which are better than the channelled abilities' buff structs (found by logging every var while channelling).
  - **Timing:** `COMBATV2_CHANNEL_START_CLIENT` and `COMBATV2_CHANNEL_END_CLIENT` are VarClients holding the client Logic tick the channel started and ends on, so the timing is exact. `COMBATV2_COOLDOWN_CHANNELLING_END_EFFECT_CLIENT` is a server tick before `COMBATV2_CHANNEL_END_CLIENT` (686328 against 686358 for Assault), but isn't used: it also moves when Endless Assault turns a channel into a DoT on the target, while the start, `COMBATV2_CHANNEL_END_CLIENT`, the `COMBATV2_CHANNEL_*` VarPlayers and the end reason (left at 1) all stay put and the game shows no channel bar. Timed from that end, Assault read as a 17.4 s channel with 4.2 s left. The DoT has its own VarPlayers: `COMBATV2_CHANNEL_TO_DOT_ACTIVE_DOT` (the ability's struct, -1 when none), `_NPC_TARGET` and `_ITERATION` (1 to 3, a hit every 2 server ticks).
  - **Running or not:** `COMBATV2_CHANNEL_END_REASON` is -1 while it runs. It's set to 1 on the end var's tick when the channel completes, and to something else when it's cut short, which ends it straight away. No cut-short value has been seen yet.
  - **One tick past the last hit:** the game's own channel bar runs a server tick past the last hit, until `COMBATV2_CHANNEL_ITERATIONS` resets to 0, which is `COMBATV2_CHANNEL_END_CLIENT` (Assault's reset at 686358). Rapid Fire reads 4.8s and Snipe 1.8s from it, matching the game's bar (logged in game). Snipe's end is set again a Logic tick earlier as it fires (694430 to 694429), which would make it 1.78s, so moves of the end under half a server tick are ignored (`END_JITTER_TICKS`). The channel vars start on the ability's use tick.
  - **Which ability:** `COMBATV2_CHANNEL_ABILITY_STRUCT` is the ability's struct. Its `COMBATV2_ABILITY_ID` and `_PARENT_STAT` give a key that's the same for every version (Greater Flurry, Bloodlust and DoT variants), built with `abilityCatalogue.Key(id, skill)` (the one place that format lives) and read with `channel.Key()`, which stays on the last channel's ability once it's over. The struct can arrive a moment after the start time, so it's re-read for a server tick or so after each start.
  - **Casts:** a cast (`COMBATV2_ABILITY_CHANNEL_IS_CAST`; only Snipe, which charges up and then fires) reads as the time so far, rounded up, so its bar fills up rather than draining.
  - **Sources:** "Any channel" (`channel_any`), plus one per channelled ability (`channel_<ability>`). A channel icon behaves like a buff's. Each one's `movedFrom` holds its old buff id (`buff_combatv2_ability_<ability>`), so auras saved with that id follow it.
- **Bar display:**
  - `fillDirection` (Fill direction: the Icon's linear wipe directions, `iconOptions.WIPE_DIRECTIONS`, right by default) is the edge the fill grows from; ticks run across it. Width and height share one range (8 to 600) so a bar filling up or down can be tall.
  - `hideWhenEmpty` hides the bar while the value is 0 (an idle channel or buff, a ready cooldown), except while unlocked.
  - `showIcon` puts the source's icon at the `iconSide` end, as a square the bar's height; frame, fill, text and ticks sit in a body layer beside it, while the root keeps the full width for anchors and dragging.
  - `showTicks` (smooth sources only) marks every 0.6s server tick in `tickColour`, so a channel bar shows the game's ticks (Rapid Fire 8, Snipe 3). Marks are left out when closer than 4px.
- **Orb display** (`orb`): a circle filled to curr/max like a bar, with text nodes, Invert fill, Smooth fill and Hide when empty. There's no way to draw a circle, and a sprite showing one of our images draws untinted whatever its `rgba` (it reads back as set; seen in game), so every circle is a RadialProgressOverlay masked with `Shapes/circle.png` and tinted by its `rgba`, which works for the colour but ignores the alpha byte (`#00000000` drew black), so `tint` also sets the radial's own `alpha` (0 to 1) from it. The mask is assigned once the radial is sized (one assigned at 0 by 0 draws nothing) and `Start(0, 1, flags)` follows (`shape`). A radial draws what's left of the way round, so `curValue` 0 shows the whole circle and the fill radial gets `1 - fill`; it sweeps clockwise from the top, and `FLIP_HORIZONTAL` (`fillAnticlockwise`) anticlockwise (both seen in game). The border is a ring, so a see-through background doesn't show a disc behind it: `resources/Rings/ring_<k>.png` are 22 white rings whose thickness is 0.004 × 1.25^k of their width (made by a short Python script), and `ringFor` picks the one closest to the border's thickness over the orb's size (within about 12%). The ring is drawn over the background and fill, which reach halfway under it (`fillInset`, half the border): edge to edge, the ring's soft inner edge and the circle's soft outer edge left a see-through seam, and the nearest ring can be a little thinner than the border. The ring is hidden at 0. A linear fill's length is measured inside the border, so the part under the ring doesn't count; it reaches under the ring at the edge it grows from, and at the far edge once full. `fillStyle` linear (saved as `vertical` when it only filled upwards; `FromSaved` renames it) shows a full fill-coloured circle through a layer as long as the fill, against the edge `fillDirection` grows from (the Icon's linear wipe directions, up by default): the layer clips it. Each style's parts are made when first used. `showIcon` (Show icon) puts the source's icon (following `SetDetails`) between the background and the fill, so a see-through fill colour sweeps over it like the Icon display's swipe. An image can't be masked to a shape in the client (layers clip to upright rectangles, a sprite takes no mask, a `ui.Canvas`'s sliced `AddSprite` drew nothing, and Lua has no pixel access; all probed or documented), so the icon is a `SourceIcon`, sprite or item, as the largest square inside the circle. `dimWhileActive` (Desaturate while on cooldown / inactive, labelled as the Icon display's, off by default) greys it as the Icon display does: the icon's grey copy (`resources/GreyIcons`, looked up once per icon) laid over it, being the same shape, else a darkening tint (`DIMMED_TINT`), as for items. Made late or shown again, it lands out of place, so it sets `partsMade` and `RaiseParts` puts the background, icon, grey copy, fill and border back in order next frame. The fill's parts set `partsMade` too, being made after the ring, and any part shown again goes through `showPart`, which does the same. It's square (`width` = `height`, one Size in the editor).
- **Texts are fields only** (`Auras/Helpers/text-template.lua`): a text shows the source's values and never typed text, so a condition can't make an aura say something the game doesn't (such as what pressing an ability would give). A template is one field (`$value`, `$max`, `$percent`, `$stacks`, `$charges`, `$name`, `$ammo`, `$keybind`, `$target`, `$level`, `$hitChance`, `$weakness`), or two with a separator (` / `, ` - `, `: `, listed by their symbols). The editor shows fields by their Title case labels (Value, Max, Ammo); a template is saved as a string of their ids (`"$value / $max"`) so saves, sharing and condition values keep their form. A template that isn't valid (a damaged save, a hand-made paste) shows as the default (`textTemplate.Parts`). Texts were once typed, with placeholders (`$current`, `$arrow`, `$arrows`) among free text, and a missing one meant `$current / $max`. `Auras/Store/text-migration.lua` is the only code that knows that: `MigrateRecord` keeps a typed text's first two fields, and the separator between them if it's one of ours, in the aura's text, its nodes' and its Text changes' values. It runs on saved records before `FromSaved` while the index's `textsVersion` is below 2; the load then marks every aura unsaved and requests a save, and the index records version 2 once every aura has been written. Imports run it (`auraStore.MigrateTexts`) on exports whose `version` is below 2 (`FIELD_TEXTS_VERSION` in `aura-share.lua`). Nothing else converts old texts. Adding a second field picks its separator (`DefaultSeparator`: ` / ` between two numbers, `: ` after `$name`, else ` - `), which can then be changed and stays when either field changes. `$percent` is value / max × 100, rounded to the text's `percentDecimals` (0 to `MAX_PERCENT_DECIMALS`, 3; a text field shared by the aura and its text nodes like `decimalsBelow`, clamped when formatted so a pasted value can't break it), with a `%`; a max of 0 reads 0%. The editor's Percent decimals slider shows only while the template has `$percent`, so changing whether it does rebuilds the tab. A new aura's text is `$value` (the Text display's `$name: $value`). The editor's `UI/Controls/text-picker.lua` (Display tab, and a condition's Text change) lists the fields the aura's source fills (`dataSources.FillsTextField`: `$value`, `$max`, `$percent` and `$name` for every source, `$charges` for abilities, `$stacks` for buffs with a stacks var, `$ammo` for the quiver, `$keybind` for abilities and special attacks, `$eofKeybind` for special attacks, the target fields (`$target`, `$level`, `$hitChance`, `$weakness`) for target sources), plus the one picked if another source's. The fields beyond values, name and ammo reach the displays as one `TextInfo` table (`SetDetails`' last argument, passed through to `textTemplate.Format`): a target source's `TargetInfo`, an ability's keybind, or a toggled buff's `compactValues` (see the buff bar notes). `$keybind` is the keybind of the ability's first slot on the action bars (see The action bars), or for a special attack the Weapon special attack slot's (sprite 26105), with `$eofKeybind` ("EOF Keybind") the Essence of Finality special's (10231): the bars show those sprites whatever the weapon (`special-attacks.lua`; `DataSource.eofKeybind`, read with `$keybind` in `sourceKeybind`), read only for auras whose text shows it (`MountedEntry.showsKeybind`, set when mounted and again as conditions apply: an aura without conditions is never applied after mounting, so on mount alone it never showed its keybind; and `sourceKeybind` in the aura manager), once a step, and kept as a table replaced only when it changes, so displays notice without a table made every frame.
- **Time formats** (`textTemplate.TIME_FORMATS`): a text's `timeFormat`, a field shared by the aura and its text nodes, says how `$value` and `$max` are written when the source's values are times (`DataSource.timed`: cooldowns, timed buffs, channels, a timed variant): `clock` (hh:mm:ss, hours left off under an hour: `5:59`, `0:45`; with the text's `bareSeconds`, Just seconds under a minute, minutes left off too: `45`; `offersBareSeconds` in the list), `seconds` (ss), `tenths` (ss.ms: tenths below the text's `decimalsBelow`, 0 to `MAX_DECIMALS_BELOW` (120), whole at or above it) and `units` (mm[unit]: the largest of d, h and m that fits, rounded down within it, else seconds, as the buff bar writes timers) and `ticks` (server ticks of 0.6 s: with the text's `fullTicks`, Only full ticks, the whole ticks left, rounded down, so 2.9 s is `4` and the last tick reads `0`; off, rounded up to count the tick under way, `5`; `offersFullTicks` in the list). The editor labels each with an example only (`11:22:33`, `360`, `360.2`, `6m`), which says enough, bar ticks, labelled `Ticks`, as an example would read as seconds. Every format but ticks rounds up to whole seconds first (bar ss.ms's tenths), so a running timer never reads 0 and all of them move on together: 59.9 s is `1:00` and `1m`, 5:59 is `5m`, 3599.1 s is `1:00:00` and `1h`. Timers reach the text already rounded up to a tenth (`GameData/Trackers/game-clock.lua`), so a whole tick count drops up to a tenth of a second after the tick ends; rounded up, the count is exact. `fullTicks` is on by default, so loading takes a missing one as on (`~= false`) and sharing leaves it out when on. Values that aren't times (resources, stacks, a toggled buff's compact count) ignore it and show as the source gives them, as do `$percent`, `$stacks`, `$charges` and the target fields. A timed buff whose value is its stacks until its timer runs (`whileUntimed`: Electrified) has those stacks written as a time too (`0:03`, `3s`), as nothing tells the display which it is. Displays tell `TextNodes:Apply` whether the source is timed, and `textTemplate.Format` takes a `TextStyle` (template, format or nil for plain numbers, `decimalsBelow`, `bareSeconds`, `fullTicks`, `percentDecimals`): a drawn node is one, and the Text display keeps one. A format id it doesn't know (a newer version's) writes as ss.ms. The editor shows Time format only for a timed source whose text shows `$value` or `$max`, then the format's own options: Just seconds under a minute for one that offers it (`OffersBareSeconds`: hh:mm:ss), Only full ticks for one that offers it (`OffersFullTicks`: ticks) and Show decimals below for one with decimals (`HasDecimals`: ss.ms). It rebuilds when the format changes, or when the text starts or stops showing a time. New texts are ss.ms with decimals below 10 s.
  - **From Limit decimals:** formats replaced the `limitDecimals` checkbox (decimals only below `decimalsBelow`; off, decimals at any value). A record without `timeFormat` is from before them: `auraTexts.MigrateLimitDecimals` (in `FromSaved`, so saves and imports alike) gives the aura and each node ss.ms, keeping `decimalsBelow` where the limit was on and making it 120 where it was off (the same under 2 minutes, whole seconds above), with a node's missing options taken from its aura as saved, then drops `limitDecimals`. A save is migrated again on each load until that aura is next saved. So that a new export is never taken for an old one, sharing keeps a record's `timeFormat` even at its default (`KEPT_AT_DEFAULT`; a node's is left out at its aura's), import turns an unknown one into the default rather than nil, and `LoadDefaults` loads its blank record with one. Import still accepts `limitDecimals`. An older version importing a new export drops `timeFormat` and shows decimals at any value.
- **Text display:** the aura's text on its own (`$name: $value` by default), using the Text section's font, size, colour and time format. Its box grows to fit the text (`fontCatalogue.Measure`) up to `maxWidth`, past which the text wraps. It's re-measured whenever the text changes, its width rounded up to 4px so ticking digits don't resize it constantly, and it's placed again from its anchor. It sizes itself (`sizesItself`), so its `aura.width`/`height` are nominal; the editor's position limits use the live size from `auraManager.DisplaySize`. It shares `hideWhenEmpty`, `showIcon` and `iconSide` with the bar, and adds `textAlign` (left, centre, right) and `textShadow`.
- **Text nodes** (`Auras/Displays/Parts/text-nodes.lua`): Bar and Icon (`usesTextNodes`) draw any number of value texts, the aura's `texts` list. A node has the aura's own text field names (`showText`, `textTemplate`, `textColour`, `textFont`, `textSize`, `timeFormat`, `decimalsBelow`, `bareSeconds`, `fullTicks`, `percentDecimals`) plus a `key` and an `anchor`/`x`/`y` on the display's box (offsets right and up, as an aura's on screen). An Icon's nodes each have `hideWhenReady` too (Hide when ready, or Hide while inactive for a buff: the Icon editor's `hideWhenReadyLabel`), blanking that node while the cooldown is ready or the buff inactive (`TextNodes:SetValues`' `ready`). It was once the aura's `hideTextWhenReady`, for every text: a new node's default copies an aura's old setting (`auraTexts.New`), so loading and importing give the nodes it, and `MoveHideWhenReady` then drops the aura's. They're drawn in list order, so a later one sits over an earlier one. Their components are made as needed and kept (restyled on every `Apply`, spare ones hidden); each only reformats when its values change. They're drawn in a layer of their own beside the display's root, not in it, as a layer clips what's in it and the root is only the box, so texts running past it were cut off: the layer is 400px (`SPREAD`) bigger than the box on every side and made with the first text, one more component per display. Placement keeps it with the root (`overlay`, offset by `overlayX` to a Bar's body): moved in `moveTo`/`SetLayoutPos`, hidden with it, raised with it when dragged, and the manager stacks it right after its root. Keys are never reused, counting keys conditions still name, and a change naming a removed text shows as such in the tab. Being outside the display, they're always over its parts (a Bar's ticks, an Icon's swipe). Switching a Bar or Icon to Text copies its first node's text fields onto the aura. The store gives a Bar or Icon one node from its own text fields if it has none (`auraTexts.Ensure`, on load, create and type change), pointing its text conditions at it, and saves node colours as hex (`auraTexts.Convert`). The Text display keeps the aura's own fields. In the editor each node is a section (`buildTextNodes` in `display-tab.lua`: the Text options, which work on a node as on an aura, plus Anchor point and X/Y offsets) with move, duplicate and remove buttons, then Add text.
- **Segmented bar display** (`segments`): a row of small bars, one per stack, filled up to the source's stacks (buffs) or charges (abilities), else its current value. Sources don't say how many stacks a buff can have, so the count is the aura's `segments`. `grow` (right, left, down, up, or centred horizontally or vertically: the filled segments are the middle of the row, spreading both ways, and a short last row is centred), `perRow` wraps (0 never), `showEmpty` off hides the unfilled ones (all show while unlocked). `sizeBy` "segment" sizes each segment; "total" fits a row into `totalLength` (spreading the remainder so it's exact), so a condition changing `segments` keeps the length. Condition changes have a `number` kind (with `min`/`max`) for that. The box is the size of every segment so it doesn't move as stacks change, except in a dynamic group with `showEmpty` off, where it shrinks to the filled segments (`fitBox`) so the group packs it to what's showing; it sizes itself (`sizesItself`). For a cooldown (`state` "cooldown", timed), the segment the next charge goes in fills along the grow direction as it recharges (`fillPartway`, from the time left over its total, smooth), so Surge with one charge shows the second recharging; it shows even with `showEmpty` off. Its only text is optional, on that segment: `showProgressText` (Show progress text, the Text section's checkbox in place of Show text: a type editor's `showTextOption`) draws the aura's own text template, font, colour and time format there (one text node built from them, `progressTexts`, drawn beside the root as Bar and Icon texts are, its overlay offset to that segment with `overlayX`/`overlayY` and `syncOverlay`; `$name`, `$ammo` and `$target` come through `SetDetails`), so the editor's Text section appears only for cooldown sources (`usesText` may be a function of the aura).
- **Icon display:** a cooldown is desaturated while running and its swipe covers what's left. A buff is the other way round: desaturated (or hidden, `hideWhileInactive`) while inactive, with the swipe covering the time that's gone. `hideWhileActive` hides it while active instead, until the time left drops to `showActiveBelow` seconds (0: stays hidden). Every hide option is ignored while the aura is unlocked, so it can be moved. Other sources never dim, and their swipe covers what's missing. Over a timer the radial times itself (`AUTOMATIC`, started once and checked against the source each server tick); over anything else (stacks, resources: a source that isn't `timed`) it's drawn by hand like the Orb's radial fill (`drawRadialByHand`: `Start(0, 1)` without `AUTOMATIC`, then `curValue` set to the part not covered on each change, covering what the linear wipe would). Saved Icon auras on such sources that never picked a swipe switched from the linear wipe to the radial with this, as agreed (the default is Radial, which used to fall back). Some buffs' icons are swapped by the game's scripts (their structs set `COMBATV2_BUFF_ICON_OVERRIDE`: Death Spark, Bloodlust, Perfect Equilibrium, Crimson Salvo, the modified prayer boosts and others), so their struct's icon isn't always what the buff bar shows. Three of them have a dull `BUFF_ICON_..._INACTIVE` sprite as their struct's icon (the only three such sprites), while the bar shows the coloured one, the same name without `_INACTIVE`: Bloodlust (23876, coloured 23875), Death Spark (30128, 30127) and Soul Reave (35069, 35068). `ICONS` in `buff-data.lua` gives each the coloured one as its icon, coloured by default, with its grey copy for Desaturate while inactive and conditions. The other script-swapped icons aren't handled. It reveals its mask sprite, normally the icon's own; an item icon (`iconObject`, drawn by a sprite of its own) has no sprite id, so its radial is masked with `Shapes/pixel.png` (`maskSprite.sprite`, an image) and sweeps the whole square, falling back to the linear wipe if that's refused (untested in game). The Swipe choices are only those the source can draw (`Icon.SwipeStylesFor`, `DrawnSwipe`, which the display uses too): only None for an on/off buff (`onOff`: no timer and no stacks, so 1 of 1, or the count the buff bar shows under it, which isn't an amount to sweep either). `iconColour` (Icon tint, white by default) is multiplied into the icon, greyed or not, and darkening multiplies with it, so a tint survives dimming. `backgroundColour` (Background colour, the field Bars and Segmented bars use too, so it shares their condition change) fills the square behind the icon, black by default; it shows through transparent sprites and around item icons, so it goes grey (`maths.GreyColour`) while the icon is greyed, as the Orb's background does. Icons switched from a Bar before this kept the Bar's 70% black, so `FromSaved` resets an Icon's background at exactly that value (`dropBarBackground`).
  - **Chosen icon:** an Icon can show an icon the player picks in place of its source's: `iconSprite` (a sprite id) or `iconItem` (an item id, which wins if both are set), each `iconOptions.SOURCE_ICON` (-1) for none (`iconOptions.ChosenIcon`). They're display options with defaults, so loading fills them in, switching type resets them and exports leave them out unless one is set. The display swaps the chosen icon in for the source's details in `Apply` and `SetDetails` (`shownIcon`), so dimming, the radial's mask and `$name` work as before; a chosen sprite greys with its shipped grey copy if there is one, and an item only darkens. The editor's Appearance section shows its name ("Icon: default" until one is chosen) with Choose, and Reset once one is set.
  - **Only icons the game uses are offered**, as some sprites crash the client when drawn. A proof of concept took a typed sprite id or name on a button press (typing `20184` as it changes would draw sprites 2, 20, 201 and 2018 on the way); the picker replaced it. Items have no icon sprite (the dragon scimitar's only sprite, `MARKETPLACE_ICON_WEAPON_DRAGON_SCIMITAR`, is a 340 by 340 shop image), so an item is chosen as an item. `GameData/Catalogues/icon-catalogue.lua` lists every ability's icon from the ability catalogue (base, greater, recast stages and command, each also found by the ability's struct name, `AbilityEntry.structName`), every buff's and debuff's (a sprite an ability or another buff also shows is listed once, found by every name; so is an item a buff shows, as the buff, found by the item's own name and config name too, and left out of the wearable items in searches), and every wearable item (`item-slot-data.lua`, labelled as the Load tab's item picker labels them). Items that aren't worn (potions, runes) aren't offered, as no list of them ships. Imports keep a chosen sprite or item only if the catalogue offers it (`dropUnofferedIcon` in `aura-share.lua`), so one typed into edited JSON is never drawn; a buff's sprite imported before the buffs have loaded is dropped too.
  - **Search** (`iconCatalogue.Search`): every word typed must be in the name or the struct or config name, in any case, with underscores as spaces, so `dragon scimitar`, `scim drag` and `DRAGON_SCIMITAR` all find it. Names starting with what's typed come first, then the rest, each in listed order: abilities, buffs, debuffs, then items, each by name. The 20,000-odd items' names and config names are read in the background the first time the picker opens (a slot's names a Logic tick, then 1,000 config names a tick) and kept for the session; closing the picker before then stops it, and the next opening starts over. Until then the picker says it's loading items, and searches again when they're in.
  - **The picker** (`UI/Windows/icon-picker.lua`): a fixed-size window, as wide as 8 columns of icons need with the same room between the last and the scrollbar as before the first (`WINDOW_WIDTH`, from PrettyUI's 8px frame and its scrollbar 13px in from the scroll view's right edge), that opens beside the main window, level with its middle and a gap away: on its right, or its left if the right has no room, or with room on neither side, in the middle of the game area (`openingPosition`; the main window's bounds reach it through the editor's `windowBounds`, passed to type editors' `appearance`). It has a search field, two lines naming the icon under the mouse (its name, then its kind and struct or config name) and a grid of the results. The grid builds only the rows on screen plus one either side, two sprites a cell (an item needs a sprite of its own), and reuses them as it scrolls: a result's cell is its place in the results wrapped round the cells, so scrolling a row changes only that row's cells. PrettyUI's scroll view can't be given a new content height, so each search makes a new one (`showResults`), holding only a spacer for the results' height and the scrollbar; the cells and outlines sit in a layer of ours over it (`cellLayer`, clickthrough, clear of the scrollbar, clipping them to the grid) and are kept from one search to the next, moved each frame the scroll view's `scrollY` changes (`watchScroll`). The mouse wheel over a cell is passed on to the scroll view (`scrollByWheel`); over the gaps it reaches the scroll view through the clickthrough layer. Clicking an icon closes the picker and sets it, after the click's callback; the chosen icon has an outline in the grid. The picker chooses for one aura (`auraID`): every editor build closes it unless the editor still shows that aura and its type chooses icons (`TypeEditor.choosesIcon`, `iconPicker.CloseUnlessFor`), so moving to another aura, deleting it or changing its type closes it. While it's open it costs about 180 parts for the grid's sprites (worked out from its size, not counted in game) plus the window's own, whatever the number of results. At the 4,096 limit it leaves out what can't be made and logs that once a session (`reportBuildFailure`): cells past the limit, or a search's scroll view (the cells are hidden, and its status line says there's too much on screen), or, if the window, search field, status lines or the grid's layers can't be made, the window, which is destroyed with whatever was made of it. Any other error still surfaces.
- **Fonts:** `id.Font` returns a value even for unknown names, so `GameData/Catalogues/font-catalogue.lua` probes families and sizes by comparing against a made-up name.
- **Colour clipboard:** the plugin API has no system clipboard access, so the colour input's Copy/Paste share one saved plugin-wide colour. Ctrl+C/V in its hex field does reach the system clipboard.

## Conditions

- An aura's `conditions` (`Auras/Registries/conditions.lua`, which documents the record) is a list; each has `checks` and `changes`. A check tests a data source: the aura's own, or one picked by data type then source (`sourceType`, `source`; a type with no source picked fails): `active` (State: true or false, or for an ability `conditions.USABLE`/`NOT_USABLE`, shown as Castable and Not castable, read from the action bars; a cooldown's State (`COOLDOWN_TYPES`: abilities, special attacks, extra action buttons) shows On cooldown and Not on cooldown for true and false, see The action bars; a usable test on an ability that isn't on a bar passes, so it never blocks; the editor offers them for `USABLE_TYPES`, and a saved check of the old `usable` kind loads as one), or `value` (seconds left for timers), `percent`, `stacks` (buffs) or `charges` (ability cooldowns) compared with a number by an operator; `conditions.ChecksFor` lists the kinds a data type has. Stacks and charges are both a source's fourth value, named for what it is: abilities have charges, not stacks. Each condition's `match` says whether all its checks must pass or any one (`all`/`any`; older saves' per-check AND/OR `join`s load as `any` if there was an OR). A condition with no checks never passes. The UI calls them checks so they aren't confused with the conditions they make up. While one passes, its `changes` set display options (`conditions.PROPERTIES`, limited per display type by `types`); later conditions win.
- **Evaluating:** `auraManager.Draw` works out which of an aura's conditions pass as a bit mask (`conditions.Mask`), reading sources through the same cache as the displays. It does so once a server tick (`gameClock.ServerTicks`), when game values change, unless a check reads a value extrapolated between ticks (a `smooth` source: cooldowns, timed buffs, channels; stacks and usable tests excepted), in which case every Logic tick (`gameClock.LogicTick`, 50 a second: those values move no faster; `conditions.NeedEveryLogicTick`, worked out when the aura or the sources change, which also forces a test on the next frame). Only when the mask changes does it re-apply the display with the changed aura (`conditions.Apply`, a copy with the overrides; the stored aura is never touched). `hidden` isn't an aura field: it goes to placement's `SetConditionHidden`. When a passing condition sets Hide (Yes or No; the last one wins) it decides over the display's own hide options, so "Hide: No" shows an icon that Hide while active (or Hide when empty) would hide; when none does, the display's own options decide. Like the display's own hide options, it's ignored while the aura is unlocked.
- **Saving:** conditions are nested tables. The store copies them on save and load (`convertConditions` in `aura-record.lua`), encoding colour values in changes as hex like top-level colours and dropping unknown properties. `Duplicate` deep-copies. Condition sources count as used (`auraStore.UsedSources`: loaded first; `MigrateSources`: migrated with `CurrentID`).
- **Editor:** each condition is a collapsible section, with remove, duplicate and move buttons in its header (the editor's `section` takes `buttons`; every section header is stretched to fit them, `tallHeader.Stretch` in `UI/PrettyUI/tall-header.lua`, which patches PrettyUI's collapse button). A check reads top to bottom: data type (or the aura's own source), data source (no label: `sourcePicker.Add`'s `label` is only given by the Trigger tab), then one row of what's tested, "is", and what it must be ("Value is Below 5", "State is Active"; `UI/Controls/split-row.lua`, so choices don't start with "Is"). Operators are short words (Below, At least, ...): game text reads `<` as a tag, the combo's box shows escapes like `<lt>` as typed (its `selectedLabel` is read-only), and characters outside the game's character set show as "?". Values are typed in a plain field so decimals work (0.6 for a tick). Groups have no conditions.
- **Per-text changes:** Show text, Text colour and Text are `perText`: on a display with text nodes a change names its node (`text`, the node's key; picked under the option, unlabelled, as the change's value is), and `conditions.Apply` copies that node to change it. On the Text display they change the aura's own fields.
- **New property:** add it to `conditions.PROPERTIES` with a `kind` the tab knows (colour, bool, text, number; a number takes `min`/`max`, or `limit` to read its max from the display type's `limits` in `Auras/Displays/Options/`) and the `types` that have it; the display must already apply that field in `Apply`.

## Load

- An aura's `load` (`Auras/Registries/load-options.lua`, which documents it) decides whether it's loaded at all; one that isn't isn't mounted. It has fixed `options` (`OPTIONS`: In combat, Weapon style, Item equipped, Skill level, Ability unlocked; an In a group option, read from the `GROUP_INVITED_NAME` VarClient, was tried and dropped, as it didn't follow joining or making a group reliably), each `{ enabled, value }` and only tested while enabled, and custom `checks` (a condition's checks, all of which must pass; one with a data type but no source picked yet, `conditions.IsComplete`, is skipped, so adding a check doesn't unload the aura). Everything enabled must pass. Nothing enabled (or no `load`) means always loaded. Unticked options keep their value, so ticking one again brings it back, but aren't tested. Most compare their `read()` with the value; Item equipped (`passes`, `picksItem`) has a slot (a `wornEquipment.SLOTS` key; the Aura and Wings slots aren't offered, `UNOFFERED_SLOTS`, though a setting naming one is still tested) as its value and the item worn there as the setting's `item`, picked in the Load tab with `UI/Controls/item-picker.lua`: a fast typeahead of the slot's items by name (`itemSlots.Named`, which reads their names on first use: ~5,000 for the main hand) and "Use worn item". It passes until an item is picked, and changing the slot clears the item. It matches that exact item, so another version of it (augmented, degraded, dyed) doesn't count. Weapon style (`picksHands`) has a second dropdown, the setting's `hands` (`HANDS_CHOICES`: Any, Dual wield, 2 handed; nil, from before it existed, is Any), which must match `playerState.WeaponHands` as well as the style: `twoHanded` when the main hand's worn item is in `two-handed-data.lua` (`itemSlots.IsTwoHanded`), `dualWield` when both hands have a weapon style and the off hand does damage (`COMBATV2_OFFHAND_STRENGTH` above 0, as a defender has a melee style too), else `oneHanded`. It's read once a step, and only for settings that aren't Any. Import keeps `hands` only if it's one of the choices. **Comparing options** (`readNumber`; Skill level is the first, and new ones that compare a number should follow it) compare their chosen thing's number now (`readNumber(value)`, read once a step per choice; nil fails) with the setting's `op` (a `conditions.OPERATORS` id) and `number`, through `conditions.Compare`, as a condition's check does; the Load tab shows the shared `UI/Controls/comparison-input.lua` under the dropdown. Missing `op`/`number` are `DEFAULT_OP`/`DEFAULT_NUMBER` (At least 0), so ticking one doesn't unload the aura. Import keeps `op` only if it's an operator and `number` only if it's a number. Skill level's value is a `SkillType` key (`playerState.SKILLS`, alphabetical, Constitution for `HITPOINTS`), read as the level now, boosts and drains included (`Player.GetLevelGameplay`). An option's `choices` can be a function, for a list read from the game (`loadOptions.Choices`; `DefaultValue` is its `default` or else its first choice, set when it's ticked; the Load tab shows no dropdown while the list is empty). A saved value the dropdown doesn't list shows as "Not listed", or "Choose one..." with none picked (`choiceCombo`'s `missingLabel`), never as the first choice, as that isn't what's tested. **Ability unlocked** (`GameData/Trackers/ability-unlocks.lua`) lists every ability in the ability catalogue by name, each followed by "Greater ..." if it has a greater version (ids: the ability's source id, or `greater:` and it), then "is" and Unlocked or Not unlocked (`picksUnlocked`, the setting's `unlocked`: nil or true wants it unlocked, false not). An ability is unlocked when its `COMBATV2_ABILITY_LEVEL_REQ` is met in its skill, levelled rather than boosted (`Player.GetLevelCapped`), and its own `<struct name>_UNLOCKED` flag, where that var exists (a quest or codex unlock, e.g. Vital Drain), is set; a greater version also needs its greater unlock flag (`AbilityEntry.greater.unlockVar`). The level's skill comes from the struct's name (`LEVEL_SKILLS`: Attack and Strength abilities share parent stat 1, as the parent stat is the combat style: 1 melee, 3 Ranged, 4 Magic, 5 Defence, 6 Constitution, 7 prayers, 29 Necromancy), so `MELEE_` abilities skip the level check. Answers are kept for a server tick.- **Evaluating:** `auraManager.Draw` works out every enabled aura's load state (`updateLoaded`, before the sync, once a Logic tick, reading sources through the same cache and each option once, `loadOptions.NewStep`) and resyncs when one changes. Like conditions, it's tested once a server tick unless a load check reads an extrapolated value, and again whenever the aura changes. An unlocked aura always loads, so it can be found and moved. Load checks' sources count as used, like conditions' (`auraStore.UsedSources`, loaded first; `auraStore.MigrateSources`, migrated with `CurrentID`). Groups (both kinds) have load options too: one that isn't loaded isn't mounted, so nothing in it is either. A group has no source of its own, so its checks only offer data types. A new load check starts on the first data type with no source, for any aura.
- **Game data:** `COMBATV2_PLAYER_IS_IN_COMBAT` (a varbit) for combat, `COMBATV2_MAINHAND_STYLE` / `COMBATV2_OFFHAND_STYLE` for the weapon's style (the main hand's, or the off hand's when the main hand is empty): 6 melee, 8 ranged (9 too: Malachi's tooth, a crossbow), 1 magic, 37 necromancy, 7 nothing, -1 an empty off hand (seen in game; one- or two-handed and augmented don't change it). They may be weapon categories, so other weapon types could differ; `player-state` has a temporary `DEBUG` log of unknown values (once each), to come out once the values are confirmed.
- **Editor:** `UI/Editor/load-tab.lua`: each option is a checkbox with its value's dropdown under it, shown only while ticked (ticking rebuilds the tab). Where something goes with the value, the two share that row half each (`splitRow`), as the text picker's fields do: Weapon style's hands, Item equipped's item (its typeahead, with "Use worn item" on the row below), or "is" and what it must be (Skill level's comparison, `comparisonInput.Add` with `x`/`xAnchor`; Ability unlocked's Unlocked/Not unlocked). The options are listed at the top with no section (they'll be grouped into categories later), then a Custom checks section built with `conditionsTab.AddChecks`.
- **New option:** add it to `OPTIONS` with `choices`, a `default` and a `read()` (a tracker read); the tab picks it up.

## Sharing

- `Auras/Sharing/aura-share.lua`: Export turns an aura or group (with everything in it) into text; Import adds it back as new auras. There are three formats, all holding the same records:
  - **JSON**, `{"runeAuras": 3, "records": [...]}` (`runeAuras` is the format version, and says what it is), on one line with a space after each comma and colon, field names in full and in `KEYS` order (what an aura is first). Export uses it whenever it fits one input field (`auraShare.BOX_LIMIT`, 9,999), so it can be read and edited as code and pasted back; a single aura or a group of up to about 20 does. `Auras/Sharing/json.lua` writes and reads it: strings are the game's bytes, and every byte outside printable ASCII (and `<`, which game text reads as a tag) is written `\u00XX` and read back as that byte, so the text is plain ASCII; a `\u` above `00FF` reads as `?`. It must be pasted on one line: an edited copy laid out over several lines is cut at the first line break, so edit it on one line. The panels' hints and Import's messages are kept short ("Bad JSON: expected : at character 52.", "Missing part: 2."): the player knows what they just did.
  - **`RA2:`** + base64 of the same JSON with no spaces and field names swapped for short codes, LZW-compressed, for anything bigger. Of the encodings measured on 44 real exports (705 auras), this was the smallest: about 9% shorter than `RA1`'s serializer form (JSON lists carry no keys and numbers no markers), while compressed JSON with full names was about 25% longer. It has no spaces or line breaks.
  - **`RA1:`** + base64 of the records serialized (`Auras/Helpers/serializer.lua`) with short codes, LZW-compressed: what older versions exported. Import still reads it, chunked by spaces as they wrote it or not.
  - The prefix (or `runeAuras`) carries the format version, so a later format can still read these, and a newer one is refused with a message.
- **Records:** `auraStore.ExportRecords` gives the saved form (`auraRecord.ToSaved`, as `Save` writes: colours as hex), the exported aura first and each group before its contents, moved to the top level with its offset turned into a screen one so it lands where it was. Nothing session-only (`unlocked`) goes with it. Fields at the value loading would give them anyway are left out (`auraStore.LoadDefaults`, `TextDefaults`: what `FromSaved` fills in, so they come back exactly), and so are fields its display type doesn't use (a type it used to be: switching type resets them anyway; `ALWAYS_KEPT` lists the ones with no default; `KEPT_AT_DEFAULT` the ones kept even at it: `id`, `display` and `timeFormat`, see Time formats). Unticked load options are left out too, and a load with nothing left in it (`dropUntickedLoadOptions`): they don't load or unload anything, and what was picked in them means nothing to whoever imports it. Saves keep them, so ticking one again brings back what was picked. A group's or dynamic group's own text fields (`auraStore.AURA_TEXT_FIELDS`, the fields a text node shares with an aura) are left out too, `timeFormat` with them (`dropGroupTexts`): every record has them, but groups draw no text, so they'd only carry whatever the group was saved with. Loading takes such a group for a record from before time formats and gives it their old decimals, which it doesn't use either. `auraStore.AddImported` loads them through `auraRecord.FromSaved`, like saved auras (so the usual conversions apply), with new ids. A record keeps its group only if that group came earlier in the list (no cycles) and `CanHold`s it; the rest, the exported aura first, go at the top level (never into the selected group: a group imported into the one it came from was easy to miss), where Export placed them on screen. They come in locked.
- **Short codes:** `KEYS` in `aura-share.lua` is append-only: a name's code is its place in the list (A, B, ... Z, AA, ...), so moving or removing one would misread older exports. Its order is also readable JSON's field order.
- **Untrusted text:** imports are only parsed (`json.lua` and `serializer.lua`, never `load`), with limits on size, depth, values, records, list lengths, string lengths and numbers; `lzw.lua` refuses output past 4 MB. Every field is checked against the type it should have (`FIELDS`, display types' `defaults`, text node fields, source options (`auraRecord.CopySourceOptions`, which loading uses too), and checks, changes and load options against the known kinds, operators and properties, and an Icon's chosen sprite or item against the icon catalogue, see Icon display) and dropped if it's wrong (a time format not known is made the default instead, see Time formats), before the store sees it: a wrong-typed value would otherwise reach a display that does maths with it every frame. **No custom text:** a text is only ever a template of the source's fields (see Texts are fields only). Displays already draw only `textTemplate.Format`, which shows anything that isn't a template as the default, and `$name` is only a registered source's name. But with exports readable and editable as JSON, Import and Export also make any text that isn't a template the default (`resetCustomTexts`): the aura's own, its text nodes' and its Text changes' values, on import after old typed texts are migrated to fields. Each shows exactly as it did, but typed words are never stored or passed on, where one loosened check would let them show. An aura's name is the one free text, typed in the editor: it shows in the window's list and, with its angle brackets stripped (`gameText.Plain`), on a group's box only while it's unlocked. Import never errors (it's wrapped in `pcall`); it returns a message for the player instead, and for JSON that can't be read, what's wrong and at which character. The store fills gaps in text nodes from a new node's defaults, with unique keys.
- **Parts:** base64 too long for a box is split into parts (`RAP1:<checksum>:<i>/<n>:` then a slice, up to 9,900 characters each): Export shows a box per part, and Import takes several boxes, in any order. Pasting part of a multi-part export and pressing Import gives as many boxes as it has, keeping what was pasted and naming the missing parts; the checksum of the whole refuses parts of different exports and damaged ones. Import strips whitespace from base64 and parts, but only trims JSON, whose strings can hold spaces.
- **UI:** `UI/Windows/share-panel.lua`: a panel in the editor's place (the main window's `openPanel`, as New's) holds Import's paste box and Export's string to copy. Import has two tabs, Examples and Custom (`importTabs`, kept for the session so it opens on the tab last used; a failed import opens on Custom). Examples lists the example auras (`Auras/Sharing/examples.lua`: each its export as a JSON long string, a name, a description and `iconSource`, a data source whose icon shows beside it; a row shows the icon, the name in subheading page text and the description under it). Clicking a row, or Custom's Import button, opens the preview (`UI/Windows/import-preview.lua`, `previewTexts` in the share panel), a window beside the main one like the icon picker: a description (the example's, or for a paste what it adds, "Adds 3 auras and 1 group.") under a title (the example's name, or the paste's first aura's), then each aura that isn't a group drawn by its own display code (`Auras/Displays/display-modules.lua`) under its name, in a layer of its own, then Import (which adds it) and Cancel. An export that can't be read doesn't open it: Custom shows the problem, with as many boxes as a multi-part export needs, as before. `auraShare.Preview` reads an export into auras without adding them (`auraStore.PreviewImported`). Previews show sample values (`SAMPLE_SHARE` of 100, or 30 seconds for a timed source; a Segmented bar that share of its segments), not the source's own, which are mostly empty out of combat, and have their hide options turned off; conditions and load options aren't applied. Only the source's details (name, icon, ammo) are live. A preview's layer is made tall, the display made and fed, then the layer cut to its height (plus `AURA_MARGIN` around it and its text nodes' largest offsets, for texts outside its box) and the display applied again so it's centred. A preview wider than the window's content (bars go to 600px, segmented bars to 1,200) has the window made again at that width, within the game area: the window is laid out for the width it's made at. Every aura is drawn, with no cap. Import and Cancel are made before the previews, and each preview in a holder layer of its own under `pcall`, so one that can't be drawn (the parts limit, or a display error, logged once) removes only itself and ends the previews with "The rest can't be shown here.", and Import still works. If the window itself can't be made, `importPreview.Open` returns false and the share panel imports straight away, so a preview never stops an import. The examples' rows take clicks through an empty text over each row (`UI/Controls/button-cursor.lua` gives it the button pointer, as the aura list's rows have), and the main window builds a showing panel again when sources change (`OnSourcesChanged`), so the examples' icons appear once the buff list has loaded. The examples' JSON is kept as exported; to change one, export it in game and paste the export in. Custom has the paste box (or one per part, see Parts) at a fixed height, any problem above it, and the Import button under it, which opens the preview. Copying and pasting use Ctrl+C/V in the text field, as there's no clipboard API. The game's input fields take at most 9,999 characters whatever `maxLength` asks for (a raw `ui.InputField` clamps any `maxLength` above it, and refuses content longer than its limit), and a paste is cut off there and at the first line break, so exports are kept short and on one line. The boxes wrap and scroll: an input field wraps only when `text.maxLines` is above 1 (PrettyUI makes its fields with 1, and 0, unlimited for a `ui.Text`, keeps an input field on one line too), so it's set to 255, the most it holds. An input field breaks its lines anywhere, between any two characters, not only at spaces as other game text does, so base64 fills each line with no spaces added (JSON's words get split at line ends too). Its scrollbar sits inside its text area and covers the last few characters of each line; that's accepted (copying is unaffected), as nothing else was better: a wider right content margin moves the scrollbar in with the text, a scrollbar that never hides still covers it, a thin one looked wrong, and a hidden one left no sign the box scrolls. PrettyUI's text field has no multi-line option of its own (its methods: `GetText`, `SetText`, `SetPlaceholder`, `SetDisabled`, `SetTooltip`, `SetDefaultSprite`), nor its views a text area. Export is a button under the name in the editor's General section (`onExport`).

## Adding things

- **New data source:** add it to its type's builder in `Auras/Registries/Sources/` with a `type` from `TYPES` in `Auras/Registries/data-sources.lua`, reading through a `GameData/Trackers/` module (and listed from a `GameData/Catalogues/` one if the set comes from game config). A new kind of data gets a new entry in `TYPES`, a builder module in `Sources/`, and a list in `data-sources.lua`'s `rebuildSources`. Cooldown sources are generated from `GameData/Catalogues/ability-catalogue.lua`, buff sources from `GameData/Catalogues/buff-catalogue.lua`. `abilityCatalogue.FALLBACK` is only used while the config can't be read; its entries have no `id` (sources are named by their var), and their `legacyID`s are migrated through `cooldowns.RENAMED_IDS` in `Auras/Registries/Sources/cooldowns.lua`.
- **Editor modules** can list options in `rebuildOn` that change which of their controls show (Segmented bar's `sizeBy`, `grow`); changing one rebuilds the editor. A module that keeps a control between callbacks (Segmented bar's total length, whose minimum follows the count) clears it in `beginBuild`, called at the start of every build: a collapsed section isn't rebuilt, so the old control would be a destroyed one.
- **New display type:** add its options module under `Auras/Displays/Options/` (with `defaults`, which the store copies onto auras that lack them, and `limits`) and register it in `Auras/Registries/display-types.lua`; add its drawing module under `Auras/Displays/` and list it in `DISPLAYS` in `Auras/aura-manager.lua`. Add type-specific editor controls in a module under `UI/Editor/Types/` and register it in `TYPE_EDITORS` in `UI/Editor/aura-editor.lua`. Use `Auras/Displays/Parts/placement.lua` for positioning and dragging. Keep `width`/`height` meaningful: the editor and anchors use them, and changing display type resets them to the new type's defaults. An editor module sets `usesFillColour = false` if the generic Fill colour doesn't apply.
- **New aura option:** add a default in `Auras/Store/aura-record.lua` (`FromSaved` and `NewAura`) or in the display's `defaults`, apply it in the display's `Apply`, and add a control to the right editor section.

## Groups

- A group is an aura record with `display = "group"` (`auraStore.CreateGroup`) with no size: it's a **point** everything in it is placed from, so it moves as one and stays together when the screen resizes. Any aura or group can have a `group` field naming its parent, and groups nest. Order is each record's place in the store's list (`Children` keeps it).
- **Positions in groups:** a top-level group's anchor and x/y place its point as an aura's would (for a point with no size; new groups start on the centre). A group inside a group has no anchor, only an x/y offset from its parent's point. An aura inside a group is placed at a plain x/y offset (right and up) from the group's point, and its anchor is the point of the aura that attaches there (`anchors.FromPoint`/`ToPoint`; the editor calls it "Attach point"). `auraStore.ScreenPoint(aura, w, h)` gives any record's point on screen (an aura's is its attach point; sizes cancel out, so the store needs only the game area's size).
- **Keeping things in place:** `auraStore.Move(id, groupID, beforeID, w, h)` reorders and regroups in one call; it and `Delete(id, w, h)` of a group keep what moves where it is on screen by converting through `ScreenPoint` (dynamic groups too: an aura's own offset is kept in place, though unused while it's in one). `DeleteWithContents(id)` deletes a group and everything in it, at any depth, and `DeleteAll()` every aura and group (`DescendantCount` says how many that is). Without the game area's size they only regroup. `Move` refuses cycles. A plain group's **Reset offset** button (`auraStore.ResetGroupOffset`) puts its point back on its anchor (or its parent's point) and moves its contents' offsets the other way, so nothing moves on screen; dynamic groups don't get it, as their contents grow from the point.
- **Old saves:** before group points, a group's x/y shifted its contents, which kept screen anchors. The save carries `positionsVersion`; older ones are converted once by `auraStore.MigratePositions`, which `auraManager.Draw` calls when it first knows the game area's size. Until then `Save` keeps the old version number.
- **Dynamic groups** (`display = "dynamicGroup"`, `auraStore.CreateDynamicGroup(groupID)`) count as groups (`IsGroup`), so the tree, collapsing and drag-into work the same, but:
  - **Contents:** they hold auras only, no groups of either kind (`auraStore.CanHold`; `Move` refuses, and the list doesn't offer the drop).
  - **Position:** their point, placed as any group's, is where their auras grow from. Their auras' own anchors and x/y are ignored while inside (placement skips them when `layoutManaged` is set, and they can't be dragged alone).
  - **Layout:** `Auras/Displays/dynamic-group.lua` builds on the Group display (same layer, drag box and bounds), with `grow` (right, left, down, up, centred horizontally or vertically), `spacing` and `align` (start, centre, end, across the grow direction). Each Logic tick (and after a sync), once values have shown or hidden displays, `auraManager` lines up each dynamic group's auras that are showing (mounted, loaded, and not hiding themselves through `setHidden`) in list order, so they close up as buffs come and go. Its box (`contentBounds`) fits only the auras showing, as a hidden one is left wherever it last was. While the group is unlocked (as it is while selected), every enabled aura in it loads and shows (`Placed.forceShown`, set by `syncLevel`, which overrides hide options and conditions without making them draggable), so its whole layout can be seen and the box fits all of it. A Segmented bar shows its empty segments then too.
  - **Load:** an aura that isn't loaded (see Load) isn't mounted, so the group closes up around it.
  - **Editor:** `UI/Editor/Types/dynamic-group.lua` adds a Layout section (the editor's `layout` hook); Position is a group's. Its auras' Position section just says the group places them.
- `auraManager` mounts each level under its parent group's layer (`syncLevel`), remounting an aura when its parent changes, and gives each group the box around its contents. A hidden group hides everything in it. Stacking follows the list: every sync brings each display to the front in list order (within its group's layer), so auras lower in the list draw over ones above them, and an aura raised by dragging drops back into place. Top-level auras sit in a full-size layer of our own (`container`) rather than straight in the game area: displays made directly in the game area landed behind everything when shown again and didn't reliably come to the front. Group layers are full-size and stay at 0, 0 (a dragged group's layer moves until release, then goes back around its new point), so every layer shares the screen's coordinates. The manager hands each group's `point` to its contents (`groupPoint`, through `new` or before `Apply`); a group makes a new point table only when it moves, so contents re-apply exactly when their group moved.
- The list shows every aura as a tree, groups indented with their contents; a group's arrow collapses it (remembered as `listCollapsedGroups`). Groups are marked only by their arrow; the row under the mouse and the selected row get a tint and a gold name. Clicking a row selects it for the editor. Dragging a row's name moves it to where it's dropped: the top or bottom half of an aura's row means before or after it, a group's middle half means into it (at the end) and its top or bottom quarter before or after it (the top of its contents when it's open), and below the last row is the end of the top level. A line or a group highlight shows where it will land. An invisible hit area over each name takes presses (the name's text ignores the mouse) and expands over the whole list on the first hold, so the hold keeps reporting however fast the mouse moves, without moving the text. New swaps the editor for a choice of what to make (`NEW_ITEMS` in `main-window.lua`: Bar, Icon, Text, Segmented bar, Orb, Group, Dynamic group); what's made goes into the selected group, or beside the selected aura, and is selected.
- Editor modules can drop sections with `usesSource`, `usesAppearance` and `usesText = false`, and drop the Text section's "Show value text" with `usesShowText = false` (Text); groups keep only Name and Position. The Position section works out the rest from where the aura sits (top level, in a group, in a dynamic group). `displayTypes.Selectable()` leaves Group out of the type list.

## Conventions

- **Editor layout:** every control has its label on its own row above it. Checkboxes are the exception because they carry their own text. Controls size from the window rather than using fixed widths: fill the row, or pin to the right with a negative `x` and `xAnchor = 1`. The window resizes in both directions.
- **Tooltips:** none on a control's label, a colour field, or a checkbox whose text already says it (Invert fill, Smooth fill, Hide when empty, Show icon, Desaturate). Elsewhere only where the control doesn't say it, and then a few words, not a sentence ("Type to filter"). Icon-only buttons get their action's name ("Duplicate").
- **Section controls** are added through the `view` passed to each section's build function. It indents rows by the single `SECTION_INDENT` constant and exposes `contentPadding`, which `number-input` reads. The editor builds each tab page through `host` (the page being built); use it directly only for section headers.
- **Spacing and colour constants** shared between UI files live in `UI/ui-constants.lua`; a file may alias them locally (`local GAP = uiConstants.GAP`). Ones used by a single file, like `SECTION_INDENT` in `UI/Editor/aura-editor.lua`, stay at the top of that file.
- **Rebuilding UI from inside a control's own callback:** defer it to the next frame with `UI/next-frame.lua` (`nextFrame.Run(id, fn)`, `nextFrame.Cancel(id)` on teardown; e.g. `requestRebuild` in the editor, `requestRender` in the main window and the ribbon panel), so the control isn't destroyed mid-callback. Rebuilds keep the scroll position.
- **PrettyUI ids:** every PrettyUI root we construct (`Window.new`, `SimpleView.new`, `Tabs.new`, and the import preview's Cancel `SimpleButton.new` on its own row) passes a `categoryID`, and controls added through a view's `Add...` methods, or constructed in a PrettyUI control or view (`heroIcons.Button`, the tab strip's arrows), inherit it from where they go. Roots in the editor area (the editor's tabs, header and home page, the New and Share panels) pass `uiConstants.PRETTYUI_EDITOR_CATEGORY` (`"auto"`: each control gets ids of its own, which builds a long tab much faster). Windows, the views on their content and the ribbon panel pass `uiConstants.PRETTYUI_CATEGORY` (nil, PrettyUI's default): `"auto"` there broke dragging the main window in PrettyUI 1.3.0 (the comment on them says how). Plain components (`ui.Layer.new` and the rest) go only in a content host (a window's or view's `content`, a tab page, a list's `viewport`) or in our own layers there. One inside a PrettyUI control (a button's `root`, a scrollbar's `thumb`) is made with `prettyui.NewComponent(ui.Text, parent)`: under `"auto"` a plain one there can take an id the control's own parts use, and crash the client.
- **Colours** are `0xRRGGBBAA` integers. Name colour fields `colour` or `...Colour`: the store saves any such field as a hex string automatically.
- ComboBox entry ids must be integers. Map list positions back to registry ids (`comboEntries`).
- Giving ComboBox entries an `order` makes PrettyUI use its filtering `OrderedComboBox`: a typeahead. The data source picker uses it, with a "Choose a source..." placeholder because that combo otherwise shows its first entry when nothing is selected. A plain combo box (no `order`) is the client's own combo field, whose dropdown shows about 5 rows and scrolls whatever its `dropdownMaxVisibleEntries` or row height; the typeahead draws its own, taller list, which also looks better. So every combo box is a typeahead (`fastTypeahead.Add`): `choiceCombo.Entries` gives each entry its place in the list as its `order`, keeping the list's own order, and a placeholder takes order 0. Three things about PrettyUI's typeahead are patched (`passMouseThroughArrow` in `fast-typeahead.lua`, on its `button`, `input`, `parent`, `open`, `_Open` and `_Close`): its arrow (`button`) caught the mouse wheel, so the editor didn't scroll while the mouse was over it, and clicking it didn't focus the text box as the plain combo's did; and an open dropdown stays where it was while its view scrolls the box away. So while closed the arrow is `clickthrough`, the text box (`input`) is widened under it (`SetSize(0, 0, 1, 1)`), and releasing a click on the text box opens the dropdown (on the release: opened on the click itself, PrettyUI closed it again). While open the arrow takes the mouse again, and an `ONTIMER` listener on the text box closes the dropdown once its view has scrolled (the content's `y` or its holder's `scrollY` changed): a wheel listener on the view only heard the wheel once it couldn't scroll further, as PrettyUI's scroll view keeps it. Only one dropdown is open at a time (`openCombo`): opening one closes the other, and while open an `ONCLICK` listener on the view's content (`parent`) closes it on a click elsewhere in the view (the client gives the mouse's position but not its buttons, so clicks are only heard through components).
- **Read game data through `GameData/game-api.lua`.** The client can update underneath the plugin, so every read of game data (config, vars, `id.*` lookups, interface components and their params, `Player.*`, `VarTransmit` payloads, `Plugin.resources`) is guarded there. `gameApi.Read(what, fn, ...)` returns nil instead of erroring and logs the first failure of each `what`, so a read the game broke shows once in the console; `gameApi.Try(fn, ...)` is the quiet version for reads expected to fail sometimes (names that may not exist, config before entering the game). Prefer its named helpers (`VarPlayer`, `Param`, `Struct`, `ParamValue`, `Component`, `Font`, ...); for anything new, pass a named function, not a closure, so hot paths allocate nothing, and call native methods with `:` inside it (see Pitfalls). Keep the guard to the game reads themselves: our own code runs outside it, so its bugs still surface. Our own UI components (setting `rgba`, `SetPos` and so on) aren't guarded.
- **Shared helpers:** `gameApi.GameArea()` and `gameApi.GameAreaSize()` look up the game area everything is drawn in. `gameApi.Cached(lookup, name)` remembers a var or param config looked up by name, for reads every frame; it doesn't remember misses, since config may not be readable before entering the game; `gameApi.CachedVarPlayer(name)` reads a VarPlayer through it. `game-clock` holds the tick constants (`LOGIC_TICKS_PER_SECOND`, `SECONDS_PER_SERVER_TICK`, `LOGIC_TICKS_PER_SERVER_TICK`), `TicksToSeconds` (exact for whole seconds) and `ToTenths`, the round-up-to-a-tenth every timer uses. Id and var name prefixes live with what makes them: `abilityCatalogue.SOURCE_ID_PREFIX`, `STRUCT_PREFIX` and `COOLDOWN_VAR_PREFIX`, and `buffCatalogue.SourceID`/`IsSourceID`.
- **Code standards:** follow `CODE-STANDARDS.md`. Comments are concise and explain why. Every function has a LuaCATS doc block (`---@param`, `---@return`, with types). Shared record shapes are a `---@class` defined once, in the file that owns them (`Aura` in `Auras/Store/aura-record.lua`), and referred to by name elsewhere. Each file owns one area. The whole codebase follows it.
- Debug logging is prefixed `DEBUG` and gets removed once it has served its purpose.

## Pitfalls already hit

- **Call native methods with `:`, never pass one as a value.** `pcall(struct.HasParam, struct, param)` crashed the client to desktop on load, though in plain Lua it's the same as `struct:HasParam(param)`. Why isn't known, and only a struct's method has been tried, so treat every native object's methods the same way. To call one through `pcall` without a closure per call, wrap it in a named function that uses `:` (`local function hasParam(s, p) return s:HasParam(p) end`, then `pcall(hasParam, struct, param)`). Plain functions on tables, such as `config.Struct.FromID(id)`, are fine with `.`.
- **`ui.Sprite:SetAssociatedObject` takes the object id alone, as a whole number.** The stubs show an optional quantity, but `SetAssociatedObject(id, 1)` failed with sol's "no matching function call takes this number of arguments". Set `associatedObjectQuantityMode` (in the stubs) after it, as setting the object may reset it.
- **RadialProgressOverlay** has `curValue`, `initialValue`, `endValue`, `maskSprite`, `progress`, `rgba`, `alpha` and `Start`.
  - It draws nothing until it has a mask: `maskSprite` is read-only, but the SpriteData it returns is live, so set `radial.maskSprite.spriteID`. It reveals that sprite radially, tinted by `rgba`; the Icon display masks the icon itself with a dark tint.
  - `Start(initial, end, flags)` sets `curValue` to `initial`, so `progress = (cur - initial) / (end - initial)` starts at 0. Writes to the value properties before `Start` are ignored; `curValue` can be written once it's running (confirmed in game), so the Icon display writes it after `Start` to start partway, reading it back and falling back to sweeping from full over the time left if it didn't stick.
  - Flags (`ui.RadialProgressOverlayFlag`): `AUTOMATIC = 1` makes `curValue` count up in real seconds by itself; `REVERSE = 2`, `FLIP_HORIZONTAL = 4`, `FLIP_VERTICAL = 8`. So one `Start(0, total, AUTOMATIC)` plus a `curValue` write animates a whole timer from wherever it is. `REVERSE` draws the other slice but still clockwise from the top, so its edge turns the other way, and `FLIP_HORIZONTAL` draws the slice anticlockwise. So the Icon sets `REVERSE` when the dark slice is the time left (a cooldown, or an inverted buff) and `FLIP_HORIZONTAL` when that differs from Swipe anticlockwise (`swipeAnticlockwise`, offered only for the radial): every swipe turns clockwise unless that's ticked, and Invert swipe only swaps the slices. The other swipe is the linear wipe (`swipeStyle = "linear"`; saved as `"vertical"` before it had directions, renamed on load by `renameVerticalWipe` in `aura-record.lua`), with a Wipe direction (`wipeDirection`: `right`, `left`, `down`, `up`, named like grow directions after the way it grows (`right` from the left edge); `up`, the default, is the old vertical wipe).
- **PrettyUI's filtering combo box is O(n²)**: its filter calls `List:SetEntryVisible` per entry, and each call rebuilds every row. With ~150 cooldowns that froze the editor. PrettyUI's dropdown also makes a row of components for every entry that passes, so a list of thousands (a slot's 5,000 items) ran out of component ids, and with PrettyUI 1.3 a few hundred buffs ran past the client's 1-second limit on opening. Build every typeahead with `UI/PrettyUI/fast-typeahead.lua` (`fastTypeahead.Add(view, options)`): it filters with one rebuild, builds no rows while the dropdown is closed, and builds the rows itself from plain components, only those in view plus a margin (`ROW_MARGIN`), again as the list scrolls past them (its `SetScrollPosition`), with the content height still set for every match so the scrollbar is right. So no list needs a cap.
- **Syncs only redo what changed:** the store keeps a per-aura version that every change bumps (`Set`, `Edit`, moves and the other store operations). `auraManager.RefreshChanged()` (editor edits, moves) re-applies only auras whose version moved; `Refresh(isAffected)` re-applies the auras that show or check a source passing `isAffected` (`auraStore.ReadsSource`): `source-sync` passes buff or unlisted sources when the buff list changes, and ability-linked ones when a greater icon switches, as re-applying every aura each time cost two or three full passes at login. `Refresh()` with nothing re-applies everything (cooldowns rebuilt from the catalogue on entering the game, the game area resized). A sync reads every group's contents from one pass over the list (`auraStore.ChildrenByGroup`), as `Children` per group scanned the whole list for each one, twice. Stacking is redone only when the order of displays changed, a display was made or re-shown, or one was dragged.
- **Keep per-frame work in Lua**: `auraManager.Draw` runs every frame, and draws every aura once a Logic tick and after a sync (other frames would repeat the last draw). Cooldown vars are read from a cache that `VarTransmit` keeps current (`GameData/Trackers/ability-cooldowns.lua`) rather than asking the game each frame, and displays only reformat text when the value or template changes. `VarTransmit` fires for every var change in the game, so `var-changes` reads each one's name once for every listener, and the listeners use plain `string.find` checks, not patterns.
- **Sprites can be tinted (`rgba`) but not desaturated**: there's no greyscale property and no way to make sprites from pixels in Lua. Greyed-out icons are real greyscale PNGs, generated offline and shipped in `resources/GreyIcons/icon_<spriteID>.png` (reached as `Plugin.resources.GreyIcons.icon_<id>` and assigned with `sprite.sprite = image`). Item icons can't be greyed: they aren't plain sprites. Icons without a grey copy fall back to a darkening tint. `deploy.ps1` copies `resources/`.
- **Don't read buffs' values off the game's buff bar.** Its text only says whole seconds or whole minutes (`1m` is anything from 1:00 to 1:59, while seconds round up), it shows a buff a tick before its number, and a buff the player has filtered out of it never shows. Working around that needed estimates and fragile range tracking, so buffs' timers and stacks come from their vars only; the bar only says whether a buff its vars say is running still counts as active (see Buffs). Debuffs come from their vars alone.
- **Some sprites crash the client when drawn** (rsprite's README says so, without naming them). Draw only sprites the game itself uses for the thing shown (an ability's or buff's icon); never walk sprite ids drawing each one.
- **An interface has 4,096 dynamic component ids, shared by every category.** Everything we draw (the auras in the game area and the main window, which PrettyUI puts in the same interface, `TOPLEVEL_V2`) shares them: 322 auras plus their list rows ran out ("invalid dynamic ID, expected a value between 0 and 4096"). Ids are reused after a destroy, so what counts is how many components are alive. Making layers in another category doesn't help: a new category gets "no available dynamic IDs" once the interface's pool is used. There's no API to make an interface of our own, and passing an explicit `dynamicID` (with category 0 or our own) to `ui.Layer.new` on the game area crashed the client to desktop, so ids can't be managed by hand either. PrettyUI's controls are expensive (a list row of its sprite buttons, label and box was about 44 parts), so the list rows are plain components placed by hand (`addIcon`: a sprite swapping to its hover version; a text; an outline and a fill whose colour shows hover and selection: about 8 a row, with no icon tooltips), and the editor builds only the tab that's showing (switching tab rebuilds). Measured after these changes: 328 auras (mostly Icons) used 2,247 components, about 7 each, and the open window (list, one editor tab) 422 more, so 2,672 of 4,096: room for about 200 more auras of that kind with the window open. We keep the count down and fail softly: the list builds only the rows near what's on screen (sized from the window's visible height, `listViewHeight`, not the view's, which grows with its content) (`auraList.NeedsRender`, checked each frame, rebuilds as it scrolls; rows are a fixed height, so every row's place and drop zone is worked out without building it, with spacers for the rest); displays make optional parts only when they're used (an Icon's border, grey copy, item sprite, radial and wipe, `ensurePart`, restacked into order; a Bar's border, source icon and tick layer; the Text display's icon; segments' borders), and a border is one outline rectangle (`fill = false`, `outlineThickness` drawn inwards) rather than four edges; and a display that can't be made destroys its root and is skipped, with Apply and SetValue guarded too, so reaching the limit logs one warning (`reportDrawFailure` in the aura manager; `gameApi.IsComponentLimitError` tells the limit's error from a bug) instead of an error every frame.
- **PersistentDB silently refuses a value over its size limit.** `Set` doesn't error; the old value just stays. One value holding every aura stopped saving at 49 auras (each stored fine alone), so auras are saved one key each (`aura.<id>`) with an index (`auras`: `nextID`, `positionsVersion`, `ids` in list order), only copying and encoding auras whose version moved (so auras are only changed through the store's operations, which bump it; auras just loaded count as saved) and only rewriting ones whose saved form changed. Each write is read back (numbers only need to be close: they come back with precision lost); one that didn't take is retried next save, with a warning once. The store's operations don't write straight away: they `RequestSave`, a debounce: `SavePending` saves once changes stop for `SAVE_DELAY_FRAMES` (or `MAX_SAVE_DELAY_FRAMES` after the first), since a slider drag or typing changes an aura every frame and saving each one wrote the aura and the index and read both back every frame. `SaveNow` writes at once, on leaving the game and in `PluginShutdown`. A save writes at most `MAX_WRITES_PER_SAVE` auras and finishes on the next frames (`SavePending`, from `auraManager.Draw`), writing the index last: the client stops any Lua call after 1s, and an import or a whole save of a hundred-odd auras went past it. Saves before that kept every aura in `auras.auras`; `Load` still reads that, and the next save moves them, keeping the old list until every aura's own key has taken. `Save` reads the index back too and warns once if it didn't take. `Load` reads the auras' keys `LOAD_PER_FRAME` a frame from its own Draw subscription (each read and `FromSaved` is about 0.1 ms, so 705 read at once took a 70 ms frame, the biggest part of the plugin's load), keeping the list empty until all are read and filling it at once on the frame after; `Save` does nothing until then, so it can't write an incomplete list over the save. `main.lua` starts `source-sync`, `auraManager.Draw` and the panel's count from `Load`'s callback. A load that stops short (an error in a batch, which it logs once, or `StopLoading` on unloading) leaves saves off for the session. It reads the index's ids up to the first gap, as `ipairs` does.
- **PersistentDB loses precision on large numbers.** Colours stored as numbers came back with their alpha byte rounded to 0, so bars and text turned invisible. Store colours, or any value above about 2^24, as strings. Small integers such as positions and sizes are fine.
- **Saved window state:** the main window's rect is saved as an `"x,y,width,height"` string (`mainWindowRect`), the list's width (dragged with the divider beside it) as a number string (`mainListWidth`), collapsed editor sections (`editorCollapsedSections`) and collapsed groups in the list (`listCollapsedGroups`, dropping deleted groups) through `GameData/remembered-list.lua`, as is `abilityTwoCharges`. All are clamped or validated on load.
- **PrettyUI internals:** every patch lives in `UI/PrettyUI/`. Scroll views are left as PrettyUI makes them: the scrollbar and its gutter go when nothing overflows, so the content widens (a patch to keep the gutter had no effect in game). `slider-fixes.lua` calls `Slider:_LayoutValue` on resize, because the slider doesn't re-place its thumb itself, and replaces its `_UpdateDrag` (`updateThumbDrag`, which explains why: PrettyUI's thumb drag mixed two coordinate frames). `tab-strip.lua` fits the editor's tab strip to its width: when the tabs don't all fit, only those that do are shown, between arrows at either end of the strip to scroll through them (PrettyUI's tabs' `tabs` list, `visual`/`hit`/`width`). `tall-header.lua` stretches section headers, and `fast-typeahead.lua` replaces the filtering combo box's `_Filter` (passed the typed text) and its list's `_RebuildRows` and `SetScrollPosition`, and builds rows in the shape the list's own scrolling and selection read (its header lists the internals it relies on). If PrettyUI updates, check in game that these still behave (slider thumbs, the tab strip, section headers, typeahead filtering, scrolling and picking in a long typeahead such as the item picker).
- **PrettyUI's `FancyButton` is never narrower than 225px** (two 25px end caps and a middle of at least 175px), whatever `width` asks for, and an anchored width places its label for the wrong width. In a narrow place (the 224px ribbon panel, whose scrollbar track starts at x 208, PrettyUI's scroll view `track`) use `AddSimpleButton` with a width worked out in pixels.
- **PrettyUI's `CollapseButton`** can only hold a few control types, so sections are plain headers and collapsing rebuilds the editor without that section's controls. An open section draws a faint box behind its controls (`section` in `aura-editor.lua`): rectangles made in the page's `content` layer before the controls, so they're behind them, sized from how far down the section view's controls reach (`view.bottom`).
- **Stacking quirks:** a component made this frame ignores `MoveToFront`, and a component shown again after `hidden` loses its place in the stack. So the aura manager restacks on the next frame whenever a sync made a display (every display), or a display reports `needsRestack` after un-hiding itself through `placement`'s `setHidden` (Icon's hide options, Bar's and Text's Hide when empty): then only that display and those after it in the list (`restack(from)`, from `stackIndex`), since raising those puts it back above the ones before it. A display whose texts' layer was just made asks the same way. A display that made a part over its others (Icon's optional parts) or showed one again (an Icon's `showPart`: its grey copy and radial dropped behind its black backing otherwise) sets `partsMade`, and the manager calls only its `RaiseParts` next frame (they're often made the same frame, so raising them straight away is ignored). Each cooldown use or buff gained used to restack every display.
- **Dragging** follows the cursor (`drag-follow.lua`, also used by `thumb-drag.lua` for the scrollbar thumbs of the typeahead's dropdown and the aura list, which PrettyUI drags only while the mouse is over them): `ONHOLD` and `ONRELEASE` only follow the cursor over the held component, and there's no mouse button state, so while a display is dragged an invisible catcher over the game area takes the mouse, and its `ONHOLD`s (one a Logic tick) say the button is still down. Dragging the aura list's scrollbar, the catcher heard one `ONHOLD` and then none, so the drag ended: something raised after the click covers it (probably the clicked PrettyUI window raising itself; a dropdown's thumb, drawn in the overlay above the window, wasn't affected). So the catcher is brought back to the front each Logic tick. Each moves the display to the cursor, so it stops where the button went up; no `ONHOLD` for `RELEASE_GAP_TICKS` ends the drag, and the display's own release hooks are ignored meanwhile. `Mouse.GetPosition` is in window pixels without UI scaling, so the scale is measured at the click from `xyGlobal`. Leaving the game window ends the drag, keeping the display in bounds. Without a mouse, or at the component limit, `ONHOLD` moves it from hook coordinates. The editor unlocks an aura while its Display tab is showing, so it can be dragged straight away. An unlocked display is outlined in gold 1px outside its box (`unlockedOutline` in `placement.lua`: drawn in the parent beside the root, which would clip it, and moved, hidden, stacked and destroyed with the display), so its own colours, background included, show as they will once locked. Unlocked auras catch clicks, so the editor locks it again when another tab or aura is picked or the main window closes; it only acts when that changes, so a rebuild doesn't undo unticking "Unlock to drag on screen".
- **A component that takes the mouse (`enabled`, not `clickthrough`) swallows the mouse wheel** inside a scroll view, so the view doesn't scroll while the mouse is over it. The aura list's rows forward it: `ONSCROLLWHEEL` passes `(self, scrollWheelYDelta)` (official docs), and `scrollByWheel` in `aura-list.lua` scrolls the view. The delta is positive for down, and a row (32 px) a notch matches the view's own scrolling (both seen in game).
- **The mouse cursor doesn't change while the client's console is open**, for any plugin component. Close the console before checking hover cursors.
- **There's no `os.clock()`**, nor any other clock finer than the Logic tick (20 ms), so code can't be timed in game: per-frame costs can only be reasoned about, or compared by how they feel.
- **The console reads `<...>` in logged text as markup** and drops it, so a log line like `<STRUCT_NAME 123>` prints blank. Log config names without angle brackets.
- **`require` never errors, and passes back only tables.** A module that doesn't exist (or that a reload hasn't found yet, see Running and testing) comes back as nil, not an error, and so does one returning anything but a table (`return true` gave nil). So a module that only signals something returns a table (`UI/Windows/dev-build.lua`: `{ isDevBuild = true }`). A `.lua` file at the plugin's root other than `main.lua` is run by the client on its own at load, so modules live in folders.
- **Text:** the bar sets the font before `rgba`, the same order PrettyUI's widgets use.
- **Our images can't be assigned by PrettyUI.** It's a separate plugin, so an image it assigns (e.g. passing a `Plugin.resources` image to `AddSprite`) is looked up in PrettyUI's own folder: "Failed to load resource ... unable to read data from disk", even for images our own code loads fine. Create the control with a game sprite id (a sprite takes an id or an image, never nil) and assign the image from our code (`addDivider` in `UI/Editor/conditions-tab.lua`).
