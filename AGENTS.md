# Rune Auras

A RuneScape 3 (BETA client) Lua plugin that lets players create **auras**: on-screen UI elements showing game data. An aura pairs a **display type** (how it is drawn, e.g. a bar) with a **data source** (what it shows, e.g. adrenaline). Players create and edit auras in game; nothing is shown by default.

## Before writing code

- **Read `CODE-STANDARDS.md` first**, before the first edit, not after. The rule most often missed: comments are short (one sentence is normal, three is long), and a game fact is explained once, where the code enforces it. The background and the evidence for it (what a probe found, counts, history) go in this file, not in code comments.
- **Before calling a change done,** check the diff against "Reviewing against these standards" at the end of `CODE-STANDARDS.md`. Temporary `DEBUG` probes are exempt: they're removed.

## Running and testing

- `deploy.ps1` copies every `.lua` file, `plugin.json` and `resources/` (PNGs) into `C:\ProgramData\Jagex\RuneScape-BETA\dev_plugins\rune-auras`. Reload the plugin in the client (`prl rune-auras`) to pick up Lua changes. New or changed resources, and new Lua files, need a plugin refresh (`prf`) or a client restart: a reload leaves `Plugin.resources` as it was, and doesn't find a file the plugin didn't have. It also writes `UI/Windows/dev-build.lua` there, which turns the debug options on (see `UI/Windows/debug-options.lua`); a release must not include it. It never deletes files, so remove renamed or deleted modules from the target folder by hand.
- There is no Lua toolchain installed. Syntax-check with the `luaparse` npm package (`luaVersion: '5.3'`) from a scratch directory. Behaviour can only be verified in game, so say so rather than claiming a change works.
- The client runs Lua 5.3+ (`//` and bitwise operators are fine).

## Learning the plugin API

- **Never read other people's plugins.** Jagex's AI guidelines don't allow AI to read other developers' plugin code. Don't open, extract, search or copy from installed plugins (`C:\ProgramData\Jagex\RuneScape-BETA\plugins\`) or anyone else's dev plugins, including PrettyUI's source. Learn the API from the official docs and the stubs, from this file and this repo's own code, and by probing in game.
- **Official docs:** [developer.runescape.com/rs](https://developer.runescape.com/rs/getting-started.html), Jagex's documentation of the RuneScape Client API. It has a tutorial, plugin structure, cheat commands, the API reference (Core: events, input, HTTP, `PersistentDB`; Game: player, world, inventory, config types, entities; Ui: components, layouts, style sheets; Audio, Math, Requests) and the submission guidelines. Check it first, then the stubs.
- **API stubs:** the LuaLS stubs at `../runescape-api-stubs` ([FriendlyDevelopment/runescape-api-stubs](https://github.com/FriendlyDevelopment/runescape-api-stubs)) fill in what the docs leave out, and `.luarc.json` points the language server at them. Check them before guessing at a member.
  - `types.lua` holds the globals (`id`, `config`, `var`).
  - `generated/` documents every class: config types such as `StructType`, `EnumType`, `DBTableType` and `DBRowType`, plus the `ui.*` components.
  - `csvs/` lists names by id (`Sprite.csv`, `VarPlayer.csv`, `VarClient.csv`, ...): grep them offline instead of probing in game. They lack Enum, Struct, Param and DBRow names.
- **Enumerating config:** every `id.<Type>` has `FromID(id) -> name` and every `config.<Type>` has `FromID(id) -> config`. Walking ids from 0 until a long run of misses lists every config of a type. `pairs` works too on `config.Struct`, `id.Struct`, `config.Enum`, `id.Enum`, `config.DBRow`, `id.DBRow` and `config.DBTable` (their metatables have `__pairs`): on `id.Struct` it gives each id that exists and its name, in rising order, and its iterator keeps its own place, so it can be kept and stepped a batch per `Logic` tick with other config read in between (checked in game: the same 35,926 structs as walking ids, which tries 58,616). Spread either over `Logic` ticks: there are tens of thousands of structs.
- **rsprite** (dev plugins `rsprite` and `rsprite-finder` in `dev_plugins/`): a sprite name/id lookup and search library, plus an in-game finder for browsing sprites. Use the finder to find icons while developing. Rune Auras doesn't depend on it: it isn't published (dev dependency by name only), and `id.Sprite[name]` / `id.Sprite.FromID(id)` cover what we need at runtime.
- **PrettyUI** (6398181): the UI library, injected as the global `prettyui` through `requiredDependencies` in `plugin.json`. Look it up when it's needed (see `getPrettyUI` in `UI/Windows/main-window.lua`), not at load: a dev plugin can load before its dependencies.

Key client APIs used here: `ui.Layer/Rectangle/Text.new`, component `SetPos/SetSize/Subscribe/MoveToFront/Destroy`, `ui.Hook.*`, `Event.Draw/ServerLogic/ContentLayerReady/GameStateChanged`, `PersistentDB:Get/Set/GetString/SetString`, `var.VarPlayer[name]`, `Player.*`, `id.Font.*`, `config.Enum[name]` (`.values` is a list of `{key, value}`) and `struct:GetParamValue(param)` over `struct.params`, `ui.Sprite` (`spriteID`, `rgba` tint), `ui.RadialProgressOverlay`, `formatStr`, `log`.

Reading an unknown key on a native component or `id.*` table returns nil (or a placeholder) rather than erroring, so a read can't prove a property exists. To discover an API, log the keys of `getmetatable(instance)`; that's how the radial overlay and sprite members below were found.

## Layout

Each folder holds one kind of module, so put a new file in the folder whose description fits it. Every module explains itself in its header comment; the notes below cover what's shared across files. If there's an `AGENTS.local.md` next to this file, read it too: it covers local-only tools and data that aren't shared (git-ignored).

| Folder | What goes in it |
| --- | --- |
| `main.lua` | Wires everything up and nothing more: loads auras, starts the trackers, mounts the panel, drives `auraManager.Draw` every frame, starts `source-sync`, and tears down on leaving the game and in `PluginShutdown`. Logic about any one area goes in that area's module. |
| `GameData/` | `game-api.lua`: every read of game data goes through it (see Conventions). |
| `GameData/Catalogues/` | **Lookups built once** from game config: what exists (abilities, buffs, fonts), with names, icons and ids. `font-catalogue.lua` also measures text in a font. Built at load or on entering the game, possibly in the background, sometimes cached in PersistentDB. They don't change while playing, except for one-off adjustments like greater ability icons. |
| `GameData/Trackers/` | **Continuous reads** of live state (resources, cooldowns, active buffs), polled every frame or kept current from events (`ServerLogic`, `VarTransmit`). Event-driven ones have `Start`/`Stop`, and `Reset` where they hold state that must be dropped on leaving the game; polled ones with no state of their own (`player-resources.lua`) are plain reads. `channel.lua` follows the player's current channel; `player-state.lua` reads whether they're in combat and their weapon's combat style, for load options. `game-clock.lua` is one the others build on: `TickFraction()` says how far through the 0.6s server tick the game is, from client `Logic` ticks between `ServerLogic` events, so once-a-tick values can be extrapolated. |
| `Auras/` | The core: `aura-manager.lua` (one display per enabled aura, fed values each frame; `Refresh()` after any change) and `source-sync.lua` (keeps the data sources in step with the game: lists them again as config becomes readable and the buff catalogue loads, switches greater icons, moves saved auras off changed source ids, and reports auras showing a buff that can't be tracked). |
| `Auras/Store/` | The saved auras. `aura-store.lua` is the only one files outside the folder use: lookups (`Get`, `List`, `Children`, `IsGroup`, ...), the operations that change auras, and `Load`/`SavePending`. Other files read records from `Get` but change them only through its operations: `Set` for one field, `Edit(auraID, fn)` for nested or several fields (it tidies away empty condition and load tables, touches and saves), `SetAnchor`, `Move` and the rest. It's built from the folder's other modules, each requiring only those before it: `saved-values.lua` (colours as hex, integers), `aura-texts.lua` (the `TextNode` record: new nodes and keys, their saved form, giving older auras one), `aura-record.lua` (the `Aura` record: every field documented at the top, defaults, what a group is, `FromSaved`/`ToSaved`), `stored-auras.lua` (the list, ids and versions), `persistence.lua` (each aura under its own PersistentDB key `aura.<id>`, with an index under `auras`; see Pitfalls), `groups.lua` (screen points, regrouping, `Move`, `ResetGroupOffset`, `MigratePositions`) and `shared-records.lua` (the store's side of export and import). |
| `Auras/Registries/` | What an aura can be made of, as the lists the editor picks from: `data-sources.lua` (what an aura can show, grouped by data type), `display-types.lua` (how it's drawn), `conditions.lua` (the Condition, Check and Change records, what they can test and change, and testing them) and `load-options.lua` (what decides whether an aura loads, and testing it). |
| `Auras/Sharing/` | Export and import as text: `aura-share.lua` (the format, and checking pasted text, which is untrusted) and the encodings only it uses, `base64.lua` and `lzw.lua`. The store's side is `Auras/Store/shared-records.lua`. |
| `Auras/Displays/` | One module per display type (Bar, Icon, Text, Segmented bar, Group, Dynamic group). Each display provides `defaults` and `new(parent, aura, groupPoint)` returning `Apply/SetValue/SetOnMoved/Destroy`. |
| `Auras/Displays/Parts/` | Pieces the display types share: `placement.lua` (anchored placement, dragging and hiding), `rectangles.lua` (the filled and outline rectangles everything is drawn with, the aura list and editor too), `border.lua`, `source-icon.lua` (a source's sprite or item icon) and `text-nodes.lua` (a Bar's or Icon's value texts). |
| `Auras/Helpers/` | Small pure helpers used by displays, the manager and the editor: anchors, text templates, grow directions (`grow-directions.lua`: the Grow choices and their tests, for Segmented bars and dynamic groups), `maths.lua` (`Clamp`), `game-text.lua` (`Plain`, stripping the `<` and `>` that start markup from text the player typed), and a serializer (for exports and for comparing saved forms). |
| `UI/` | `ui-constants.lua`: spacing and colours shared by the UI files. `next-frame.lua`: runs a function on the next frame (see Conventions). |
| `UI/Windows/` | Windows and their parts. The ribbon panel (`aura-panel.lua`; an edit rebuilds it only if the aura count or Delete all changed) has a button that opens the main window (`main-window.lua`), and an emergency "Delete all auras" (`auraStore.DeleteAll`) for testers stuck where the window can't help: pressing it shows a warning with Confirm and Cancel under it, and Confirm closes the window (dropping it if closing fails) before deleting. Under it, in dev builds only, "Debug options" shows `debug-options.lua`'s buttons for testing (`OPTIONS`; add one there): "Clear saved buffs" (`buffCatalogue.ClearSaved`) empties `buffStructIDs`, so a reload shows a fresh load and struct walk. A dev build is one with a `UI/Windows/dev-build.lua` module, which `deploy.ps1` writes into the deployed copy only, never the repo. The main window has New and Import along the top, the aura list on the left (`aura-list.lua`, a tree with collapsible groups) and the selected aura's editor on the right (`UI/Editor/`). Panels take the editor's place: New's choice, Import and Export (`share-panel.lua`), and Delete (`delete-panel.lua`: a list row's bin asks first, and a group with contents can go alone, its contents moving up a level, or with everything in it). A toggle at the top right switches to a single view (saved as `mainWindowSingleView`): the list fills the window and picking an aura or New swaps it for the editor, with Back in place of New and Import. Where the window opens (saved as `mainWindowRect`) is worked out by `window-rect.lua`; the divider between the list and the editor, which saves the list's width, is `pane-divider.lua`. |
| `UI/Editor/` | The aura editor: `aura-editor.lua` (the tabs and their collapsible sections), each tab its own file (`display-tab.lua`, `trigger-tab.lua`, `conditions-tab.lua`, `load-tab.lua`), and `section-buttons.lua` (`ForListItem`: the remove, duplicate and move buttons in the header of a section showing one item of a list: a condition, a text node). |
| `UI/Editor/Types/` | Per display type editor controls, registered in `TYPE_EDITORS` in `UI/Editor/aura-editor.lua`. Kept out of `Auras/` so displays don't depend on UI code. |
| `UI/Controls/` | Reusable form controls added to a window or section `view`: colour input, number input (slider plus box), choice combo (one of a few fixed `{ id, label }` choices, e.g. `choiceCombo.SIDES`), source picker (a data type's sources as a typeahead, for the Trigger tab and checks). |
| `UI/PrettyUI/` | Every patch to PrettyUI's internals, so they can all be checked in one place when it updates (see Pitfalls): `fast-typeahead.lua` (a filtering combo box that rebuilds its rows once), `tab-strip.lua`, `tall-header.lua` (section headers tall enough for buttons) and `slider-fixes.lua` (thumb drag, resizing, changing the range). |
| `resources/` | Images shipped with the plugin, reached through `Plugin.resources`. The client loads this folder by name, so it stays lowercase, like `main.lua` and `plugin.json`. Subfolders are ours and use PascalCase like every other folder (`GreyIcons/`); each becomes a key under `Plugin.resources`. `Shapes/pixel.png` is a plain white 8x8 image, stretched and tinted for thin lines (the condition divider), since PrettyUI's divider is 60px tall. |

## Game data

- **Sources and values:** a data source's `read()` returns `curr, max`, and optionally the unrounded `curr` (for a `smooth` source's Smooth fill) and `stacks` (a buff's stack count, for `$stacks`). `dataSources.Details(id)` gives its name, sprite icon and item icon. They're its own unless it has a `details()` function: "Any channel" uses that to name and show whatever is being channelled. `auraManager.Draw` reads both once per source per frame and passes the details to displays that have `SetDetails(name, icon, object)`, for `$name` and the bar's icon. Sources also say what their values are: `timed` means seconds (bar ticks, the radial swipe), and `state` is `"cooldown"` or `"active"` (buffs, channels) for the Icon display's dimming and hiding. A source that used to have other ids lists them in `movedFrom`; `dataSources.CurrentID` maps every old id (those plus `RENAMED_IDS`) to its current one, and `source-sync`'s `migrateSourceIDs` rewrites saved auras once the catalogues can be read. Cooldown and buff sources are rebuilt from the catalogues, and their ids are named after game config so they stay stable.
- **Abilities** (`Catalogues/ability-catalogue.lua`):
  - The style enums `COMBATV2_ABILITIES_<STYLE>` (MELEE, RANGED, MAGIC, NECROMANCY, DEFENCE, CONSTITUTION; there's no ATTACK or STRENGTH enum) hold `COMBATV2_ABILITY_<SKILL>_<ABILITY>` structs (spells: `MAGIC_<SPELL>`). Each has `COMBATV2_ABILITY_NAME` and `COMBATV2_ABILITY_ICON` (a sprite id) params.
  - The name normally matches the cooldown vars `COMBATV2_COOLDOWN_<name>_START/_END`. `VAR_ALIASES` maps the ones that don't, including shared cooldowns (Dive uses Bladed Dive's vars). Only abilities with both vars are listed.
  - Greater versions have an unlock flag `COMBATV2_ABILITY_<SKILL>_GREATER_<ABILITY>_UNLOCKED` and a struct of the same name with the greater icon. `GREATER_ALIASES` and `GREATER_ICONS` cover the exceptions. They switch in via `ApplyGreaterUnlocks`, which `source-sync.lua` runs (through `dataSources.ApplyGreaterIcons`) from two server ticks after the player is available, retrying each tick (up to `GREATER_MAX_TICKS`) until every flag has been read; after that `OnVarChanged`, fed from `VarTransmit`, follows flags that arrive late or change mid-session.
- **Cooldowns** (`Trackers/ability-cooldowns.lua`):
  - Timed from the `_START`/`_END` server-tick vars, using the module's own tick clock: counted `ServerLogic` events, lined up whenever a `_START` changes.
  - `_START` values sent on entering the game are ignored for a few ticks.
  - Before the clock is lined up, the highest known `_START` (every ability is registered with `Watch`) is a lower bound on the server tick, so cooldowns that ended before it already read as ready.
  - **Charges:** Surge, Escape and Barge can hold a second charge, timed by `<base>_CHARGE2_START/_END` (Barge's `_END` has no name in the var list, so it's untested). Seen in game with Surge: using a charge while both are ready sets only CHARGE2 and the ability stays usable; using the last sets the base vars, whose cooldown runs until a charge is back, and `CHARGE2_END` is when both are. So `GetCharges` is 0 while the base cooldown runs, 1 while only CHARGE2 does, else 2. Nothing says whether the player has a second charge (all read 0 until used), so an ability counts as having one once a CHARGE2 var is seen above 0, saved as `abilityTwoCharges`; until then its most is 1. Cooldown sources report charges as their fourth value (where buffs report stacks), for `$charges` and the Charges check. Their time is `GetNextCharge`: the base cooldown while no charge is left, else the second charge recharging, so Surge shows a cooldown after one use too. Its Icon isn't dimmed while a charge is left (it's usable), and an Active check on it means recharging; use Charges to test whether it can be cast.
- **Buffs** (`Catalogues/buff-catalogue.lua`, `Trackers/active-buffs.lua`): read only from the game's own vars, which are exact. Only buffs whose vars are known are listed as sources.
  - **Listing them:** every struct with a `COMBATV2_BUFF_TYPE` param is a buff (0 buff, 1 debuff, 2 neutral "stat modified" marker). A few have no type, only the buff bar's other params, and count as buffs if they have `COMBATV2_BUFF_PRIORITY` (8 in config: Living Death's `COMBATV2_BUFF_NECROMANCY_UNDEAD_INSTINCT`, Balance by Force's ability struct, and some minigame and boss buffs). Some buffs have no name or icon (`COMBATV2_BUFF_TOOLTIP_FULL_OVERRIDE`/`_ICON_OVERRIDE`): the game shows an ability's instead, linked only by a `<struct>_ABILITY_STRUCT` VarPlayer that's -1 while the buff is off, so `DETAILS_FROM_ABILITY` names the ability they take their name, icon, duration and ability key from. The name comes from `COMBATV2_ABILITY_NAME`, cleaned: tags stripped, "Name - description" cut, and sentences fall back to the struct name. The icon is `COMBATV2_ABILITY_ICON` (a sprite) or `COMBATV2_ABILITY_OBJECT` (an item). `COMBATV2_ABILITY_EFFECT_DURATION` (in ticks) gives some of them a duration.
  - **Finding the structs:** nothing indexes them all. `StructType` has no lookup by param, and the `COMBATV2_BUFF_ALL_*` enums (keyed by struct) and every other enum and DB table together hold only 264 of the 824 buff structs: combat abilities, prayers, curses and channels, but no consumables, events and the like (probed in game; `Data/buffIndexes.txt` locally). So the catalogue walks every struct over `Logic` ticks (a small batch per tick, as buffs are already listed from the saved ids) with `gameApi.StructWalk`/`NextStruct`, once per session: world hops and lobby returns don't repeat a finished walk. It saves the ids found (`buffStructIDs`). Once in game, `buffCatalogue.Load` rebuilds the list from them before the walk starts. Each buff takes dozens of guarded lookups, and all ~600 in one frame stalled it for about half a second (measured: ~24,000 lookups, a 455 ms frame). So the buffs auras use (`wanted`) are built at once, after one quick pass over the saved ids' names, so their auras show straight away rather than as placeholders. The rest load in the background, 8 a Logic tick, over about a second and a half. Every buff is built once a session (`buildEntry`, keyed by struct id), so the walk reuses what Load built and only reads new buffs from config, and a walk batch ends early after 8 of those (`SCAN_READS_PER_TICK`): 150 structs a tick is cheap only while few of them are new buffs. Source ids are `buff_<struct name>`.
  - **Timers:** a timed buff has a VarClient holding the client `Logic` tick (50 a second, `gameClock.LogicTick()`) it ends on, so the time left is `(end - now) / 50` (`COMBATV2_COOLDOWN_OVERLOAD_END_EFFECT_CLIENT`, `COMBATV2_BUFF_BLOOD_TITHE_END_EFFECT_CLIENT`). The client sets these itself, so they never come through `VarTransmit`; `active-buffs` reads them when asked. A buff is active while its end time is in the future, whether or not the game's buff bar shows it. Its max starts at the config duration (or the time left), grows with extensions of up to 2 ticks (Galeshot during Rapid Fire), and restarts on a bigger jump (a refresh).
  - **Area buffs:** Sunshine comes from standing in the ability's area, whose end time carries on after the player leaves it, so it also needs a VarPlayer varbit that's 1 while the player is in the area (`IN_AREA_VARS`: `TSD_SUNSHINE_DAMAGE`, found by logging every var change while stepping in and out). The varbit arrives a server tick after the end time, so a fresh area counts as entered for up to 2 ticks until it's first seen set. Greater versions inherit their base's. (Death's Swiftness has a `TSD_` varbit too, but it's no longer a ground effect.) The `COMBATV2_TARGET_SIDE_PANEL_PLAYER_*` varbits look like per-buff active flags but stay 0 for the player's own buffs, so they're no use.
  - **Start-timed buffs:** a few abilities' buffs (Unsullied) have no end-time var. They last `COMBATV2_ABILITY_EFFECT_DURATION` from the ability's `COMBATV2_COOLDOWN_<core>_START`, which is the cast's server tick; its `_END` is the cooldown's end, not the effect's end. They're timed with `abilityCooldowns.ServerTick()`, and the start is read from the cooldown tracker's own cache (`abilityCooldowns.VarValue`) (`startVar`, `readFromStart`). Channelled abilities (`COMBATV2_ABILITY_IS_CHANNELLED`) are left out of the buffs: they're channels (below).
  - **Toggled buffs:** prayers, curses, Bone Shield, Flow and various boosts have no timer and are switched on and off, by a VarPlayer that's non-zero while they're on (`activeVarName`). It's one ending `_ACTIVE`, or one named after the struct with or without `COMBATV2_` (prayers are varbits `COMBATV2_PRAYER_<name>` on varps 3272-3273, curses `CURSE_<name>` on 3275); `ACTIVE_VARS` lists the rest. Bone Shield's is `..._BONE_SHIELD_ABILITY_ID` (its ability's id; found by logging var changes while toggling); its `_ABILITY_STRUCT` var follows it too but reads as a struct (`UNKNOWN(-1)` when off), never a number. The tiered prayers (Thick/Rock/Steel Skin and the like) are left out: each set shares one `COMBATV2_PRAYER_BOOST_*` bit that can't tell the tiers apart. Debilitate's is `COMBATV2_DEBILITATE_NPC_UID`, the target's id or -1, so 0 and -1 both count as off. These buffs read 1 of 1 while on.
  - **Twins:** some buffs have two structs with the same name that read the same vars (a `_DUMMY` copy, as with Deflect Magic, or Berserk's buff and ability structs). `dropTwins` lists one, preferring a struct without `_DUMMY`, then one linked to an ability. The others' ids go in its `twinIDs`, which becomes the buff source's `movedFrom`, so auras saved with them keep working. Buffs without vars aren't compared.
  - **Stacks:** a few stacking buffs have a `..._STACKS` VarPlayer (`COMBATV2_BUFF_BLOOD_TITHE_STACKS`). Stacks are reported separately (the fourth value from `read`, the `$stacks` placeholder), so a buff with both reads its timer as `$current`.
  - **Finding a buff's vars:** nothing in config links a buff to its vars (no enum maps structs to vars), so the catalogue finds them by name (`endVarName`, `stacksVarName`): the struct name or its core with `_END_EFFECT_CLIENT`/`_END_CLIENT` and a few prefixes. `COMBATV2_COOLDOWN_<ability>_END_CLIENT` is the ability's cooldown, not its effect (`..._END_EFFECT_CLIENT`), so it's never used. Names that don't follow the rules go in `END_VAR_ALIASES` (or `END_VAR_PATTERNS` for families like incense) and `STACKS_VAR_ALIASES` (Animate Dead's are under `COMBATV2_MAGIC_`). A greater ability's buff has a struct named after nothing (Greater Sunshine is `COMBATV2_ABILITY_MAGIC_SOLAR_CHARGE`) but uses its base's var, so a buff without a var takes the var of another buff of the same ability: same `COMBATV2_ABILITY_ID` and `COMBATV2_ABILITY_PARENT_STAT` (the id alone is only unique within a skill: Thick Skin shares Anticipation's). Base and greater then read the same var, so both light up for either, and both show the version the player has: the catalogue notes the base as the greater buff's `baseStruct`, and the data sources link both buffs to the base ability from the ability catalogue (`greaterAbility`), whose icon follows the greater unlock as cooldowns' do. Both stay in the picker under their own names. With the start-time and toggle rules, that covers 384 of 585 buffs (channels excluded). Check a new alias in game before relying on it.

## Auras and UI notes

- **Positions:** an aura's `x/y` is an offset measured inward from its anchor (`Auras/Helpers/anchors.lua`, nine points), so right/bottom anchors count leftwards/upwards. Inside a group it's a plain offset from the group's point instead (see Groups).
- **Channels** (`Trackers/channel.lua`, data type `channel`): the game has its own channel vars, which are better than the channelled abilities' buff structs (found by logging every var while channelling).
  - **Timing:** `COMBATV2_CHANNEL_START_CLIENT` and `COMBATV2_COOLDOWN_CHANNELLING_END_EFFECT_CLIENT` are VarClients holding the client Logic tick the channel started and ends on, so the timing is exact.
  - **Running or not:** `COMBATV2_CHANNEL_END_REASON` is -1 while it runs. It's set to 1 on the end var's tick when the channel completes, and to something else when it's cut short, which ends it straight away. No cut-short value has been seen yet.
  - **One tick past the end var:** the game's own channel bar runs a server tick past the end var, until `COMBATV2_CHANNEL_ITERATIONS` resets to 0, so the tracker does too (`END_TICK_LOGIC`, 30 Logic ticks). That makes Rapid Fire 4.8s and Snipe 1.8s, matching the game's bar (both checked in game). The channel vars start on the ability's use tick.
  - **Which ability:** `COMBATV2_CHANNEL_ABILITY_STRUCT` is the ability's struct. Its `COMBATV2_ABILITY_ID` and `_PARENT_STAT` give a key that's the same for every version (Greater Flurry, Bloodlust and DoT variants), built with `abilityCatalogue.Key(id, skill)` (the one place that format lives) and read with `channel.Key()`, which stays on the last channel's ability once it's over. The struct can arrive a moment after the start time, so it's re-read for a server tick or so after each start.
  - **Casts:** a cast (`COMBATV2_ABILITY_CHANNEL_IS_CAST`; only Snipe, which charges up and then fires) reads as the time so far, rounded up, so its bar fills up rather than draining.
  - **Sources:** "Any channel" (`channel_any`), plus one per channelled ability (`channel_<ability>`). A channel icon behaves like a buff's. Each one's `movedFrom` holds its old buff id (`buff_combatv2_ability_<ability>`), so auras saved with that id follow it.
- **Bar display:**
  - `hideWhenEmpty` hides the bar while the value is 0 (an idle channel or buff, a ready cooldown), except while unlocked.
  - `showIcon` puts the source's icon at the `iconSide` end, as a square the bar's height; frame, fill, text and ticks sit in a body layer beside it, while the root keeps the full width for anchors and dragging.
  - `showTicks` (smooth sources only) marks every 0.6s server tick in `tickColour`, so a channel bar shows the game's ticks (Rapid Fire 8, Snipe 3). Marks are left out when closer than 4px.
- **Text display:** the aura's text template on its own (`$name: $current` by default), using the Text section's font, size, colour and decimals. Its box grows to fit the text (`fontCatalogue.Measure`) up to `maxWidth`, past which the text wraps. It's re-measured whenever the text changes, its width rounded up to 4px so ticking digits don't resize it constantly, and it's placed again from its anchor. It sizes itself (`sizesItself`), so its `aura.width`/`height` are nominal; the editor's position limits use the live size from `auraManager.DisplaySize`. It shares `hideWhenEmpty`, `showIcon` and `iconSide` with the bar, and adds `textAlign` (left, centre, right) and `textShadow`.
- **Text nodes** (`Auras/Displays/Parts/text-nodes.lua`): Bar and Icon (`usesTextNodes`) draw any number of value texts, the aura's `texts` list. A node has the aura's own text field names (`showText`, `textTemplate`, `textColour`, `textFont`, `textSize`, `limitDecimals`, `decimalsBelow`) plus a `key` and an `anchor`/`x`/`y` on the display's box (offsets inward, as an aura's on screen). They're drawn in list order, so a later one sits over an earlier one. Their components are made as needed and kept (restyled on every `Apply`, spare ones hidden); each only reformats when its values change. Keys are never reused, counting keys conditions still name, and a change naming a removed text shows as such in the tab. A Bar's ticks sit in a layer made before the texts, so they're always under them. Switching a Bar or Icon to Text copies its first node's text fields onto the aura. The store gives a Bar or Icon one node from its own text fields if it has none (`auraTexts.Ensure`, on load, create and type change), pointing its text conditions at it, and saves node colours as hex (`auraTexts.Convert`). The Text display keeps the aura's own fields. In the editor each node is a section (`buildTextNodes` in `display-tab.lua`: the Text options, which work on a node as on an aura, plus Anchor point and X/Y offsets) with move, duplicate and remove buttons, then Add text.
- **Segmented bar display** (`segments`): a row of small bars, one per stack, filled up to the source's stacks (buffs) or charges (abilities), else its current value. Sources don't say how many stacks a buff can have, so the count is the aura's `segments`. `grow` (right, left, down, up, or centred horizontally or vertically: the filled segments are the middle of the row, spreading both ways, and a short last row is centred), `perRow` wraps (0 never), `showEmpty` off hides the unfilled ones (all show while unlocked). `sizeBy` "segment" sizes each segment; "total" fits a row into `totalLength` (spreading the remainder so it's exact), so a condition changing `segments` keeps the length. Condition changes have a `number` kind (with `min`/`max`) for that. The box is the size of every segment so it doesn't move as stacks change, except in a dynamic group with `showEmpty` off, where it shrinks to the filled segments (`fitBox`) so the group packs it to what's showing; it sizes itself (`sizesItself`). No value text.
- **Icon display:** a cooldown is desaturated while running and its swipe covers what's left. A buff is the other way round: desaturated (or hidden, `hideWhileInactive`) while inactive, with the swipe covering the time that's gone. `hideWhileActive` hides it while active instead, until the time left drops to `showActiveBelow` seconds (0: stays hidden). Every hide option is ignored while the aura is unlocked, so it can be moved. Other sources never dim, and their vertical wipe covers what's missing. The radial swipe needs a timer and a sprite icon; item icons (`iconObject`) use their own sprite. `iconColour` (Icon tint, white by default) is multiplied into the icon, greyed or not, and darkening multiplies with it, so a tint survives dimming.
- **Fonts:** `id.Font` returns a value even for unknown names, so `GameData/Catalogues/font-catalogue.lua` probes families and sizes by comparing against a made-up name.
- **Colour clipboard:** the plugin API has no system clipboard access, so the colour input's Copy/Paste share one saved plugin-wide colour. Ctrl+C/V in its hex field does reach the system clipboard.

## Conditions

- An aura's `conditions` (`Auras/Registries/conditions.lua`, which documents the record) is a list; each has `checks` and `changes`. A check tests a data source: the aura's own, or one picked by data type then source (`sourceType`, `source`; a type with no source picked fails): `active` (true or false), or `value` (seconds left for timers), `percent`, `stacks` (buffs) or `charges` (ability cooldowns) compared with a number by an operator; `conditions.ChecksFor` lists the kinds a data type has. Stacks and charges are both a source's fourth value, named for what it is: abilities have charges, not stacks. Each condition's `match` says whether all its checks must pass or any one (`all`/`any`; older saves' per-check AND/OR `join`s load as `any` if there was an OR). A condition with no checks never passes. The UI calls them checks so they aren't confused with the conditions they make up. While one passes, its `changes` set display options (`conditions.PROPERTIES`, limited per display type by `types`); later conditions win.
- **Evaluating:** `auraManager.Draw` works out which of an aura's conditions pass as a bit mask (`conditions.Mask`), reading sources through the same per-frame cache as the displays. It does so once a server tick (`gameClock.ServerTicks`), when game values change, unless a check reads a value extrapolated between ticks (a `smooth` source: cooldowns, timed buffs, channels; stacks excepted), in which case every frame (`conditions.NeedEveryFrame`, worked out when the aura or the sources change, which also forces a test on the next frame). Only when the mask changes does it re-apply the display with the changed aura (`conditions.Apply`, a copy with the overrides; the stored aura is never touched). `hidden` isn't an aura field: it goes to placement's `SetConditionHidden`. When a passing condition sets Hide (Yes or No; the last one wins) it decides over the display's own hide options, so "Hide: No" shows an icon that Hide while active (or Hide when empty) would hide; when none does, the display's own options decide. Like the display's own hide options, it's ignored while the aura is unlocked.
- **Saving:** conditions are nested tables. The store copies them on save and load (`convertConditions` in `aura-record.lua`), encoding colour values in changes as hex like top-level colours and dropping unknown properties. `Duplicate` deep-copies. Condition sources count as used (`auraStore.UsedSources`: loaded first; `MigrateSources`: migrated with `CurrentID`).
- **Editor:** each condition is a collapsible section, with remove, duplicate and move buttons in its header (the editor's `section` takes `buttons`; every section header is stretched to fit them, `tallHeader.Stretch` in `UI/PrettyUI/tall-header.lua`, which patches PrettyUI's collapse button). A check reads top to bottom: data type (or the aura's own source), data source, Has (what's tested), Which is (choices don't start with "Is", so it reads on). Operators are short words (Below, At least, ...): game text reads `<` as a tag, the combo's box shows escapes like `<lt>` as typed (its `selectedLabel` is read-only), and characters outside the game's character set show as "?". Values are typed in a plain field so decimals work (0.6 for a tick). Groups have no conditions.
- **Per-text changes:** Show text, Text colour and Text are `perText`: on a display with text nodes a change names its node (`text`, the node's key; the tab's "Of" picker), and `conditions.Apply` copies that node to change it. On the Text display they change the aura's own fields.
- **New property:** add it to `conditions.PROPERTIES` with a `kind` the tab knows (colour, bool, text, number; a number takes `min`/`max`, or `limit` to read its max from the display module's `limits`) and the `types` that have it; the display must already apply that field in `Apply`.

## Load

- An aura's `load` (`Auras/Registries/load-options.lua`, which documents it) decides whether it's loaded at all; one that isn't isn't mounted. It has fixed `options` (`OPTIONS`: In combat, Weapon style), each `{ enabled, value }` and only tested while enabled, and custom `checks` (a condition's checks, all of which must pass; one with a data type but no source picked yet, `conditions.IsComplete`, is skipped, so adding a check doesn't unload the aura). Everything enabled must pass. Nothing enabled (or no `load`) means always loaded. Unticked options keep their value, so ticking one again brings it back, but aren't tested.
- **Evaluating:** `auraManager.Draw` works out every enabled aura's load state (`updateLoaded`, before the sync, reading sources through the same per-frame cache, and each option once a frame, `loadOptions.NewFrame`) and resyncs when one changes. Like conditions, it's tested once a server tick unless a load check reads an extrapolated value, and again whenever the aura changes. An unlocked aura always loads, so it can be found and moved. Load checks' sources count as used, like conditions' (`auraStore.UsedSources`, loaded first; `auraStore.MigrateSources`, migrated with `CurrentID`). Groups (both kinds) have load options too: one that isn't loaded isn't mounted, so nothing in it is either. A group has no source of its own, so its checks only offer data types. A new load check starts on the first data type with no source, for any aura.
- **Game data:** `COMBATV2_PLAYER_IS_IN_COMBAT` (a varbit) for combat, `COMBATV2_MAINHAND_STYLE` / `COMBATV2_OFFHAND_STYLE` for the weapon's style (the main hand's, or the off hand's when the main hand is empty): 6 melee, 8 ranged, 1 magic, 37 necromancy, 7 nothing, -1 an empty off hand (seen in game; one- or two-handed and augmented don't change it). They may be weapon categories, so other weapon types could differ; `player-state` has a temporary `DEBUG` log of unknown values (once each), to come out once the values are confirmed.
- **Editor:** `UI/Editor/load-tab.lua`: each option is a checkbox with its value's dropdown under it (greyed out until ticked), at the top with no section (they'll be grouped into categories later), then a Custom checks section built with `conditionsTab.AddChecks`.
- **New option:** add it to `OPTIONS` with `choices`, a `default` and a `read()` (a tracker read); the tab picks it up.

## Sharing

- `Auras/Sharing/aura-share.lua`: Export turns an aura or group (with everything in it) into `RA1:` + base64 of the compressed serialized records; Import adds them back as new auras. The prefix carries the format version, so a later format can still read this one, and a newer one is refused with a message.
- **Records:** `auraStore.ExportRecords` gives the saved form (`auraRecord.ToSaved`, as `Save` writes: colours as hex), the exported aura first and each group before its contents, moved to the top level with its offset turned into a screen one so it lands where it was. Nothing session-only (`unlocked`) goes with it. `auraStore.AddImported` loads them through `auraRecord.FromSaved`, like saved auras (so the usual conversions apply), with new ids. A record keeps its group only if that group came earlier in the list (no cycles) and `CanHold`s it; the rest, the exported aura first, go at the top level (never into the selected group: a group imported into the one it came from was easy to miss), where Export placed them on screen. They come in locked.
- **Untrusted text:** imports are only parsed (`Auras/Helpers/serializer.lua`, never `load`), with limits on size, depth, records, list lengths, string lengths and numbers. Every field is checked against the type it should have (`FIELDS`, display types' `defaults`, text node fields, and checks, changes and load options against the known kinds, operators and properties) and dropped if it's wrong, before the store sees it: a wrong-typed value would otherwise reach a display that does maths with it every frame. Import never errors (it's wrapped in `pcall`); it returns a message for the player instead. The store fills gaps in text nodes from a new node's defaults, with unique keys.
- **UI:** `UI/Windows/share-panel.lua`: a panel in the editor's place (the main window's `openPanel`, as New's) holds Import's paste box and Export's string to copy. Copying and pasting use Ctrl+C/V in the text field, as there's no clipboard API. The game's input fields take at most 9,999 characters whatever `maxLength` asks for, so a paste is cut off there; (the game's own cap: a raw `ui.InputField` clamps any `maxLength` above it, and refuses content longer than its limit), so exports are kept short. Fields at the value loading would give them anyway are left out (`auraStore.LoadDefaults`, `TextDefaults`: what `FromSaved` fills in, so they come back exactly), and so are fields its display type doesn't use (a type it used to be: switching type resets them anyway; `ALWAYS_KEPT` lists the ones with no default), field names become short codes (`KEYS` in `aura-share.lua`, append-only: a name's code is its place in the list), and the result is compressed (`Auras/Sharing/lzw.lua`, LZW with variable-width codes). One still too long for a box is split into parts (`RAP1:<checksum>:<i>/<n>:` then a slice, up to 9,600 characters each): Export shows a box per part, and Import takes several boxes, in any order. Pasting part of a multi-part export and pressing Import gives as many boxes as it has, keeping what was pasted and naming the missing parts; the checksum of the whole refuses parts of different exports and damaged ones. They're broken into 64-character chunks by spaces so the box can wrap them: line breaks would end a paste, as the field is single-line. Export is a button under the name in the editor's General section (`onExport`).

## Adding things

- **New data source:** add an entry to `SOURCES` in `Auras/Registries/data-sources.lua` with a `type` from `TYPES`, reading through a `GameData/Trackers/` module (and listed from a `GameData/Catalogues/` one if the set comes from game config). A new kind of data gets a new entry in `TYPES`. Cooldown sources are generated from `GameData/Catalogues/ability-catalogue.lua`, buff sources from `GameData/Catalogues/buff-catalogue.lua`. `abilityCatalogue.FALLBACK` is only used while the config can't be read; its entries have no `id` (sources are named by their var), and their `legacyID`s are migrated through `RENAMED_IDS` in `data-sources.lua`.
- **Editor modules** can list options in `rebuildOn` that change which of their controls show (Segmented bar's `sizeBy`, `grow`); changing one rebuilds the editor. A module that keeps a control between callbacks (Segmented bar's total length, whose minimum follows the count) clears it in `beginBuild`, called at the start of every build: a collapsed section isn't rebuilt, so the old control would be a destroyed one.
- **New display type:** add a module under `Auras/Displays/`, then register it in `Auras/Registries/display-types.lua`. Put option defaults in `defaults`, which the store copies onto auras that lack them. Add type-specific editor controls in a module under `UI/Editor/Types/` and register it in `TYPE_EDITORS` in `UI/Editor/aura-editor.lua`. Use `Auras/Displays/Parts/placement.lua` for positioning and dragging. Keep `width`/`height` meaningful: the editor and anchors use them, and changing display type resets them to the new type's defaults. An editor module sets `usesFillColour = false` if the generic Fill colour doesn't apply.
- **New aura option:** add a default in `Auras/Store/aura-record.lua` (`FromSaved` and `NewAura`) or in the display's `defaults`, apply it in the display's `Apply`, and add a control to the right editor section.

## Groups

- A group is an aura record with `display = "group"` (`auraStore.CreateGroup`) with no size: it's a **point** everything in it is placed from, so it moves as one and stays together when the screen resizes. Any aura or group can have a `group` field naming its parent, and groups nest. Order is each record's place in the store's list (`Children` keeps it).
- **Positions in groups:** a top-level group's anchor and x/y place its point as an aura's would (for a point with no size; new groups start on the centre). A group inside a group has no anchor, only an x/y offset from its parent's point. An aura inside a group is placed at a plain x/y offset (right and down) from the group's point, and its anchor is the point of the aura that attaches there (`anchors.FromPoint`/`ToPoint`; the editor calls it "Attach point"). `auraStore.ScreenPoint(aura, w, h)` gives any record's point on screen (an aura's is its attach point; sizes cancel out, so the store needs only the game area's size).
- **Keeping things in place:** `auraStore.Move(id, groupID, beforeID, w, h)` reorders and regroups in one call; it and `Delete(id, w, h)` of a group keep what moves where it is on screen by converting through `ScreenPoint` (dynamic groups too: an aura's own offset is kept in place, though unused while it's in one). `DeleteWithContents(id)` deletes a group and everything in it, at any depth, and `DeleteAll()` every aura and group (`ContentsCount` says how many that is). Without the game area's size they only regroup. `Move` refuses cycles. A plain group's **Reset offset** button (`auraStore.ResetGroupOffset`) puts its point back on its anchor (or its parent's point) and moves its contents' offsets the other way, so nothing moves on screen; dynamic groups don't get it, as their contents grow from the point.
- **Old saves:** before group points, a group's x/y shifted its contents, which kept screen anchors. The save carries `positionsVersion`; older ones are converted once by `auraStore.MigratePositions`, which `auraManager.Draw` calls when it first knows the game area's size. Until then `Save` keeps the old version number.
- **Dynamic groups** (`display = "dynamicGroup"`, `auraStore.CreateDynamicGroup(groupID)`) count as groups (`IsGroup`), so the tree, collapsing and drag-into work the same, but:
  - **Contents:** they hold auras only, no groups of either kind (`auraStore.CanHold`; `Move` refuses, and the list doesn't offer the drop).
  - **Position:** their point, placed as any group's, is where their auras grow from. Their auras' own anchors and x/y are ignored while inside (placement skips them when `layoutManaged` is set, and they can't be dragged alone).
  - **Layout:** `Auras/Displays/dynamic-group.lua` builds on the Group display (same layer, drag box and bounds), with `grow` (right, left, down, up, centred horizontally or vertically), `spacing` and `align` (start, centre, end, across the grow direction). Every frame, after values have shown or hidden displays, `auraManager` lines up each dynamic group's auras that are showing (mounted, loaded, and not hiding themselves through `setHidden`) in list order, so they close up as buffs come and go.
  - **Load:** an aura that isn't loaded (see Load) isn't mounted, so the group closes up around it.
  - **Editor:** `UI/Editor/Types/dynamic-group.lua` adds a Layout section (the editor's `layout` hook); Position is a group's. Its auras' Position section just says the group places them.
- `auraManager` mounts each level under its parent group's layer (`syncLevel`), remounting an aura when its parent changes, and gives each group the box around its contents. A hidden group hides everything in it. Stacking follows the list: every sync brings each display to the front in list order (within its group's layer), so auras lower in the list draw over ones above them, and an aura raised by dragging drops back into place. Top-level auras sit in a full-size layer of our own (`container`) rather than straight in the game area: displays made directly in the game area landed behind everything when shown again and didn't reliably come to the front. Group layers are full-size and stay at 0, 0 (a dragged group's layer moves until release, then goes back around its new point), so every layer shares the screen's coordinates. The manager hands each group's `point` to its contents (`groupPoint`, through `new` or before `Apply`); a group makes a new point table only when it moves, so contents re-apply exactly when their group moved.
- The list shows every aura as a tree, groups indented with their contents; a group's arrow collapses it (remembered as `listCollapsedGroups`). Groups are marked only by their arrow; the row under the mouse and the selected row get a tint and a gold name. Clicking a row selects it for the editor. Dragging a row's name moves it to where it's dropped: the top or bottom half of an aura's row means before or after it, a group's middle half means into it (at the end) and its top or bottom quarter before or after it (the top of its contents when it's open), and below the last row is the end of the top level. A line or a group highlight shows where it will land. An invisible hit area over each name takes presses (the name's text ignores the mouse) and expands over the whole list on the first hold, so the hold keeps reporting however fast the mouse moves, without moving the text. New swaps the editor for a choice of what to make (`NEW_ITEMS` in `main-window.lua`: Bar, Icon, Text, Segmented bar, Group, Dynamic group); what's made goes into the selected group, or beside the selected aura, and is selected.
- Editor modules can drop sections with `usesSource`, `usesAppearance` and `usesText = false`, and drop the Text section's "Show value text" with `usesShowText = false` (Text); groups keep only Name and Position. The Position section works out the rest from where the aura sits (top level, in a group, in a dynamic group). `displayTypes.Selectable()` leaves Group out of the type list.

## Conventions

- **Editor layout:** every control has its label on its own row above it. Checkboxes are the exception because they carry their own text. Controls size from the window rather than using fixed widths: fill the row, or pin to the right with a negative `x` and `xAnchor = 1`. The window resizes in both directions.
- **Tooltips:** only where a control's label doesn't already say it, and then a few words, not a sentence: units, a non-obvious effect or a hint ("0 for none", "Type to filter", "Positive is inwards"). Icon-only buttons get their action's name ("Duplicate").
- **Section controls** are added through the `view` passed to each section's build function. It indents rows by the single `SECTION_INDENT` constant and exposes `contentPadding`, which `number-input` reads. The editor builds each tab page through `host` (the page being built); use it directly only for section headers.
- **Spacing and colour constants** shared between UI files live in `UI/ui-constants.lua`; a file may alias them locally (`local GAP = uiConstants.GAP`). Ones used by a single file, like `SECTION_INDENT` in `UI/Editor/aura-editor.lua`, stay at the top of that file.
- **Rebuilding UI from inside a control's own callback:** defer it to the next frame with `UI/next-frame.lua` (`nextFrame.Run(id, fn)`, `nextFrame.Cancel(id)` on teardown; e.g. `requestRebuild` in the editor, `requestRender` in the main window and the ribbon panel), so the control isn't destroyed mid-callback. Rebuilds keep the scroll position.
- **Colours** are `0xRRGGBBAA` integers. Name colour fields `colour` or `...Colour`: the store saves any such field as a hex string automatically.
- ComboBox entry ids must be integers. Map list positions back to registry ids (`comboEntries`).
- Giving ComboBox entries an `order` makes PrettyUI use its filtering `OrderedComboBox`: a typeahead. The data source picker uses it, with a "Choose a source..." placeholder because that combo otherwise shows its first entry when nothing is selected.
- **Read game data through `GameData/game-api.lua`.** The client can update underneath the plugin, so every read of game data (config, vars, `id.*` lookups, interface components and their params, `Player.*`, `VarTransmit` payloads, `Plugin.resources`) is guarded there. `gameApi.Read(what, fn, ...)` returns nil instead of erroring and logs the first failure of each `what`, so a read the game broke shows once in the console; `gameApi.Try(fn, ...)` is the quiet version for reads expected to fail sometimes (names that may not exist, config before entering the game). Prefer its named helpers (`VarPlayer`, `Param`, `Struct`, `ParamValue`, `Component`, `Font`, ...); for anything new, pass a named function, not a closure, so hot paths allocate nothing, and call native methods with `:` inside it (see Pitfalls). Keep the guard to the game reads themselves: our own code runs outside it, so its bugs still surface. Our own UI components (setting `rgba`, `SetPos` and so on) aren't guarded.
- **Shared helpers:** `gameApi.GameArea()` and `gameApi.GameAreaSize()` look up the game area everything is drawn in. `gameApi.Cached(lookup, name)` remembers a var or param config looked up by name, for reads every frame; it doesn't remember misses, since config may not be readable before entering the game; `gameApi.CachedVarPlayer(name)` reads a VarPlayer through it. `game-clock` holds the tick constants (`LOGIC_TICKS_PER_SECOND`, `SECONDS_PER_SERVER_TICK`), `TicksToSeconds` (exact for whole seconds) and `ToTenths`, the round-up-to-a-tenth every timer uses. Id and var name prefixes live with what makes them: `abilityCatalogue.SOURCE_ID_PREFIX`, `STRUCT_PREFIX` and `COOLDOWN_VAR_PREFIX`, and `buffCatalogue.SourceID`/`IsSourceID`.
- **Code standards:** follow `CODE-STANDARDS.md`. Comments are concise and explain why. Every function has a LuaCATS doc block (`---@param`, `---@return`, with types). Shared record shapes are a `---@class` defined once, in the file that owns them (`Aura` in `Auras/Store/aura-record.lua`), and referred to by name elsewhere. Each file owns one area. The whole codebase follows it.
- Debug logging is prefixed `DEBUG` and gets removed once it has served its purpose.

## Pitfalls already hit

- **Call native methods with `:`, never as a field.** `pcall(struct.HasParam, struct, param)` crashed the client to desktop on load, though in plain Lua it's the same as `struct:HasParam(param)`. Reading a method off a native object as a field doesn't give a callable method. To call one through `pcall` without a closure per call, wrap it in a named function that uses `:` (`local function hasParam(s, p) return s:HasParam(p) end`, then `pcall(hasParam, struct, param)`). Plain functions on tables, such as `config.Struct.FromID(id)`, are fine with `.`.
- **`ui.Sprite:SetAssociatedObject` takes the object id alone, as a whole number.** The stubs show an optional quantity, but `SetAssociatedObject(id, 1)` failed with sol's "no matching function call takes this number of arguments". Set `associatedObjectQuantityMode` (in the stubs) after it, as setting the object may reset it.
- **RadialProgressOverlay** has `curValue`, `initialValue`, `endValue`, `maskSprite`, `progress`, `rgba`, `alpha` and `Start`.
  - It draws nothing until it has a mask: `maskSprite` is read-only, but the SpriteData it returns is live, so set `radial.maskSprite.spriteID`. It reveals that sprite radially, tinted by `rgba`; the Icon display masks the icon itself with a dark tint.
  - `Start(initial, end, flags)` sets `curValue` to `initial`, so `progress = (cur - initial) / (end - initial)` starts at 0. Writes to the value properties before `Start` are ignored; `curValue` can be written once it's running (confirmed in game), so the Icon display writes it after `Start` to start partway, reading it back and falling back to sweeping from full over the time left if it didn't stick.
  - Flags (`ui.RadialProgressOverlayFlag`): `AUTOMATIC = 1` makes `curValue` count up in real seconds by itself; `REVERSE = 2`, `FLIP_HORIZONTAL = 4`, `FLIP_VERTICAL = 8`. So one `Start(0, total, AUTOMATIC)` plus a `curValue` write animates a whole timer from wherever it is.
- **PrettyUI's filtering combo box is O(n²)**: its filter calls `List:SetEntryVisible` per entry, and each call rebuilds every row. With ~150 cooldowns that froze the editor. Build long typeahead lists with `UI/PrettyUI/fast-typeahead.lua` (`fastTypeahead.Add(view, options)`), which filters with one rebuild and builds no rows while the dropdown is closed.
- **Syncs only redo what changed:** the store keeps a per-aura version that every change bumps (`Set`, `Edit`, moves and the other store operations). `auraManager.RefreshChanged()` (editor edits, moves) re-applies only auras whose version moved; `Refresh(isAffected)` re-applies the auras that show or check a source passing `isAffected` (`auraStore.ReadsSource`): `source-sync` passes buff or unlisted sources when the buff list changes, and ability-linked ones when a greater icon switches, as re-applying every aura each time cost two or three full passes at login. `Refresh()` with nothing re-applies everything (cooldowns rebuilt from the catalogue on entering the game, the game area resized). A sync reads every group's contents from one pass over the list (`auraStore.ChildrenByGroup`), as `Children` per group scanned the whole list for each one, twice. Stacking is redone only when the order of displays changed, a display was made or re-shown, or one was dragged.
- **Keep per-frame work in Lua**: `auraManager.Draw` runs every frame for every aura. Cooldown vars are read from a cache that `VarTransmit` keeps current (`GameData/Trackers/ability-cooldowns.lua`) rather than asking the game each frame, and displays only reformat text when the value or template changes. The `VarTransmit` handler sees every var change in the game, so it uses plain `string.find` checks, not patterns.
- **Sprites can be tinted (`rgba`) but not desaturated**: there's no greyscale property and no way to make sprites from pixels in Lua. Greyed-out icons are real greyscale PNGs, generated offline and shipped in `resources/GreyIcons/icon_<spriteID>.png` (reached as `Plugin.resources.GreyIcons.icon_<id>` and assigned with `sprite.sprite = image`). Item icons can't be greyed: they aren't plain sprites. Icons without a grey copy fall back to a darkening tint. `deploy.ps1` copies `resources/`.
- **Don't read buffs off the game's buff bar.** Its text only says whole seconds or whole minutes (`1m` is anything from 1:00 to 1:59, while seconds round up), it shows a buff a tick before its number, and a buff the player has filtered out of it never shows. Working around that needed estimates and fragile range tracking, so buffs come from their vars only. Debuffs are catalogued too (`kind = "debuff"`) but there's no debuff data type yet.
- **Some sprites crash the client when drawn** (rsprite's README says so, without naming them). Draw only sprites the game itself uses for the thing shown (an ability's or buff's icon); never walk sprite ids drawing each one.
- **An interface has 4,096 dynamic component ids, shared by every category.** Everything we draw (the auras in the game area and the main window, which PrettyUI puts in the same interface, `TOPLEVEL_V2`) shares them: 322 auras plus their list rows ran out ("invalid dynamic ID, expected a value between 0 and 4096"). Ids are reused after a destroy, so what counts is how many components are alive. Making layers in another category doesn't help: a new category gets "no available dynamic IDs" once the interface's pool is used. There's no API to make an interface of our own, and passing an explicit `dynamicID` (with category 0 or our own) to `ui.Layer.new` on the game area crashed the client to desktop, so ids can't be managed by hand either. PrettyUI's controls are expensive (a list row of its sprite buttons, label and box was about 44 parts), so the list rows are plain components placed by hand (`addIcon`: a sprite swapping to its hover version; a text; an outline and a fill whose colour shows hover and selection: about 8 a row, with no icon tooltips), and the editor builds only the tab that's showing (switching tab rebuilds). Measured after these changes: 328 auras (mostly Icons) used 2,247 components, about 7 each, and the open window (list, one editor tab) 422 more, so 2,672 of 4,096: room for about 200 more auras of that kind with the window open. We keep the count down and fail softly: the list builds only the rows near what's on screen (sized from the window's visible height, `listViewHeight`, not the view's, which grows with its content) (`auraList.NeedsRender`, checked each frame, rebuilds as it scrolls; rows are a fixed height, so every row's place and drop zone is worked out without building it, with spacers for the rest); displays make optional parts only when they're used (an Icon's border, grey copy, item sprite, radial and wipe, `ensurePart`, restacked into order; a Bar's border, source icon and tick layer; the Text display's icon; segments' borders), and a border is one outline rectangle (`fill = false`, `outlineThickness` drawn inwards) rather than four edges; and a display that can't be made destroys its root and is skipped, with Apply and SetValue guarded too, so reaching the limit logs one warning (`reportDrawFailure` in the aura manager; `gameApi.IsComponentLimitError` tells the limit's error from a bug) instead of an error every frame.
- **PersistentDB silently refuses a value over its size limit.** `Set` doesn't error; the old value just stays. One value holding every aura stopped saving at 49 auras (each stored fine alone), so auras are saved one key each (`aura.<id>`) with an index (`auras`: `nextID`, `positionsVersion`, `ids` in list order), only copying and encoding auras whose version moved (so auras are only changed through the store's operations, which bump it; auras just loaded count as saved) and only rewriting ones whose saved form changed. Each write is read back (numbers only need to be close: they come back with precision lost); one that didn't take is retried next save, with a warning once. The store's operations don't write straight away: they `RequestSave`, and `SavePending` saves once changes stop for `SAVE_DELAY_FRAMES` (or `MAX_SAVE_DELAY_FRAMES` after the first), since a slider drag or typing changes an aura every frame and saving each one wrote the aura and the index and read both back every frame. `SaveNow` writes at once, on leaving the game and in `PluginShutdown`. A save writes at most `MAX_WRITES_PER_SAVE` auras and finishes on the next frames (`SavePending`, from `auraManager.Draw`), writing the index last: the client stops any Lua call after 1s, and an import or a whole save of a hundred-odd auras went past it. Saves before that kept every aura in `auras.auras`; `Load` still reads that, and the next save moves them, keeping the old list until every aura's own key has taken. `Save` reads the index back too and warns once if it didn't take.
- **PersistentDB loses precision on large numbers.** Colours stored as numbers came back with their alpha byte rounded to 0, so bars and text turned invisible. Store colours, or any value above about 2^24, as strings. Small integers such as positions and sizes are fine.
- **Saved window state:** the main window's rect is saved as an `"x,y,width,height"` string (`mainWindowRect`), the list's width (dragged with the divider beside it) as a number string (`mainListWidth`), collapsed editor sections as a comma list (`editorCollapsedSections`) and collapsed groups in the list as a comma list of ids (`listCollapsedGroups`). All are clamped or validated on load.
- **PrettyUI internals:** every patch lives in `UI/PrettyUI/`. Scroll views are left as PrettyUI makes them: the scrollbar and its gutter go when nothing overflows, so the content widens (a patch to keep the gutter had no effect in game). `slider-fixes.lua` calls `Slider:_LayoutValue` on resize, because the slider doesn't re-place its thumb itself, and replaces its `_UpdateDrag` (`updateThumbDrag`, which explains why: PrettyUI's thumb drag mixed two coordinate frames). `tab-strip.lua` fits the editor's tab strip to its width: when the tabs don't all fit, only those that do are shown, between arrows at either end of the strip to scroll through them (PrettyUI's tabs' `tabs` list, `visual`/`hit`/`width`). `tall-header.lua` stretches section headers, and `fast-typeahead.lua` replaces the filtering combo box's `_Filter` and its list's `_RebuildRows`. If PrettyUI updates, check in game that these still behave (slider thumbs, the tab strip, section headers, typeahead filtering).
- **PrettyUI's `FancyButton` is never narrower than 225px** (two 25px end caps and a middle of at least 175px), whatever `width` asks for, and an anchored width places its label for the wrong width. In a narrow place (the 224px ribbon panel, whose scrollbar track starts at x 208, PrettyUI's scroll view `track`) use `AddSimpleButton` with a width worked out in pixels.
- **PrettyUI's `CollapseButton`** can only hold a few control types, so sections are plain headers and collapsing rebuilds the editor without that section's controls. An open section draws a faint box behind its controls (`section` in `aura-editor.lua`): rectangles made in the page's `content` layer before the controls, so they're behind them, sized from how far down the section view's controls reach (`view.bottom`).
- **Stacking quirks:** a component made this frame ignores `MoveToFront`, and a component shown again after `hidden` loses its place in the stack. So the aura manager restacks on the next frame whenever a sync made a display (every display), or a display reports `needsRestack` after un-hiding itself through `placement`'s `setHidden` (Icon's hide options, Bar's and Text's Hide when empty): then only that display and those after it in the list (`restack(from)`, from `stackIndex`), since raising those puts it back above the ones before it. A display that made a part over its texts (Icon's optional parts, Bar's tick layer) or showed one again (an Icon's `showPart`: its grey copy and radial dropped behind its black backing otherwise) sets `partsMade`, and the manager calls only its `RaiseParts` next frame (they're often made the same frame, so raising them straight away is ignored). Each cooldown use or buff gained used to restack every display.
- **Dragging** uses hook coordinates relative to the dragged component (`ONCLICK` records the grab point, `ONHOLD` moves). Unlocked auras catch clicks, so the editor locks the aura again when another is selected or the main window closes.
- **A component that takes the mouse (`enabled`, not `clickthrough`) swallows the mouse wheel** inside a scroll view, so the view doesn't scroll while the mouse is over it. The aura list's rows forward it: `ONSCROLLWHEEL` passes `(self, scrollWheelYDelta)` (official docs), and `scrollByWheel` in `aura-list.lua` scrolls the view. The delta is positive for down, and a row (32 px) a notch matches the view's own scrolling (both seen in game).
- **The mouse cursor doesn't change while the client's console is open**, for any plugin component. Close the console before checking hover cursors.
- **The console reads `<...>` in logged text as markup** and drops it, so a log line like `<STRUCT_NAME 123>` prints blank. Log config names without angle brackets.
- **`require` never errors, and passes back only tables.** A module that doesn't exist (or that a reload hasn't found yet, see Running and testing) comes back as nil, not an error, and so does one returning anything but a table (`return true` gave nil). So a module that only signals something returns a table (`UI/Windows/dev-build.lua`: `{ isDevBuild = true }`). A `.lua` file at the plugin's root other than `main.lua` is run by the client on its own at load, so modules live in folders.
- **Text:** the bar sets the font before `rgba`, the same order PrettyUI's widgets use.
- **Our images can't be assigned by PrettyUI.** It's a separate plugin, so an image it assigns (e.g. passing a `Plugin.resources` image to `AddSprite`) is looked up in PrettyUI's own folder: "Failed to load resource ... unable to read data from disk", even for images our own code loads fine. Create the control with a game sprite id (a sprite takes an id or an image, never nil) and assign the image from our code (`addDivider` in `UI/Editor/conditions-tab.lua`).
